# Architecture

This document explains the high-level design decisions behind Auto Remote: why it is built the way it is, not the class-by-class mechanics.

## Core, Server, Frontend, two client heads and a web page

`Core` holds everything the server and the clients must agree on, so no app references another. The alternative, having a client depend on the server project, was rejected because it would drag server-only code into the client builds. The trade-off is that shared code must stay platform neutral.

## Server and desktop client are self-contained single-file executables

The server and the desktop client (Windows and Linux, x64) are each distributed as one executable per platform with the runtime bundled, so users install nothing else. The trade-off is a larger download than a framework-dependent build.

## Clients share one Avalonia frontend

The Android and desktop clients draw the same UI with Avalonia, so everything visual and all client logic (view models, views, theme, connection and settings services, the markdown renderer) lives in `Client/Frontend/`, a library both reference. `Client/Mobile/` and `Client/Desktop/` are only heads: the Android activity hosting the root view as a single view, and a desktop window hosting it with a plain `Main`. Both connect over secure WebSocket on the same port as the web client. `Client/Mobile/` needs the .NET Android workload to build; keeping the shared code in a plain `net10.0` library is also what lets the headless Avalonia tests reference it, since they cannot load an Android assembly. A head adds nothing of its own to behavior, which is what keeps the clients identical.

## The web client is one static file

`Client/Web/index.html` is the whole browser frontend: HTML, CSS and JavaScript with no build step, no dependencies and no serving code, so it can be dropped on any static host (or opened from disk). It mirrors the Avalonia clients' screens and behavior and connects straight to the server, over secure WebSocket (`wss`), the same transport the Avalonia clients use. It is hand-written JavaScript rather than a second Avalonia target because a single file with nothing to build is what lets it be hosted anywhere; the trade-off is that it is not covered by the .NET tests and has to be kept in step with the Avalonia clients by hand.

## Client and server must run the same version

The protocol is not versioned beyond the release, so the server tells its version in the handshake and a client that differs only offers an update or another server instead of risking calls the other side does not understand. Updating is therefore one action for both sides: a connected client updates its server first, then itself. The apps replace themselves from the GitHub release rather than through a package manager, because they ship as single files, and the web client, a file replaced by hand, takes no part.

## Access key handshake before any traffic

Clients authenticate with a single shared access key sent as the first line on the connection, before the server accepts anything else. A paired server of the swarm sends no key: its connection can only pair with a one-time code or exchange sealed packages. A per-user account system was rejected as unneeded for a single-owner server. A desktop client on the server's own machine can get the key from a channel that only the allowed operating system accounts can use, never from the fact that it connects from localhost.

## Always `wss`, on one port

Every connection is encrypted, so the key never travels in plaintext and there is no insecure mode to misconfigure. Every client, Avalonia and browser alike, speaks the line protocol as WebSocket messages over TLS on one port. A browser cannot open raw sockets, and a single transport means one port to forward and a connection that passes through anything that proxies WebSockets, such as a Cloudflare tunnel, which cannot carry raw TCP to a client that is not running its own agent. The server creates a self-signed certificate on first start (or uses a configured PFX), since a single-owner server usually has no certificate authority behind it. Without a CA the client cannot validate the certificate, so the Avalonia clients accept any certificate, trading protection against a man in the middle for needing no setup and never breaking when the server's certificate is replaced. A browser cannot skip validation, so it must accept the certificate once by opening the port in a tab (not needed behind a proxy that presents a real certificate).

## The server runs Claude Code, Codex or a local model, the client is a remote control

The server hosts workspaces and drives the local `claude`, `codex` or `opencode` executable (the last for the models on this machine), as chosen when the workspace is created, through the single prompter of the Live AI library, whose environment (commands, keys, local models, image generation) the clients edit and the server stores, so the chat is a session rather than strict back and forth: a prompt sent while the AI is working is steered into that work, and followed up with a turn of its own only if the AI did nothing about it, so none is lost to work that is just finishing, and the server can also put the AI on a loop that sends a prompt again and again. The AI works through Live AI's file tools and shell in the workspace folder, which keeps the tool's own subagents and scheduling out, so the only background work is what Live AI runs and the turn waits for. Idle sessions are closed after a while and on rename and delete, and the next prompt resumes the conversation, which the tool stores, so the server needs nothing but its stored workspaces to resume work. The conversation shown in the chat is the server's own record of what was said (a `chats` file per workspace), not the tool's stored conversation, which holds things Auto Remote has no use for such as compaction summaries. The server also reads the usage limits of each service by testing it through Live AI (and from the windows the running sessions report), cached for a minute.

## The server pushes what changes

Replies, the working state and file system changes reach the client as events on the same connection instead of being polled or held inside a long request. Events go to every connected client, which is what keeps several clients showing the same live conversation, and a client that joins mid-stream drops the first of them whose messages the history it read already ends with, so none is duplicated or lost.

## Side sessions are worktrees that an AI integrates

Several AI sessions working one folder at once would overwrite each other, so a side session works in a git worktree of its own. Bringing it back is a task for main's AI rather than a merge: main has usually moved on and may hold uncommitted work, which an AI can adapt to and a merge cannot. The same goes for the results of delegated tasks and of tasks they depend on. The AI uses git or edits files as it sees fit. This is meant to run unattended, so nothing asks for approval or checks the outcome, and nothing is kept to undo it with.

## Git runs on the server only

The server is the only place git runs: clients send commands such as `GetGitStatus` or `GitCommit` and draw what comes back, so a client needs neither git nor credentials and every client sees the same repository. Git is driven through its command line with an argument list and no shell, non-interactively (no prompts, ssh in batch mode), and a folder counts as a repository only when it is the repository's root, so a workspace inside a larger repository is not shown as one. The server computes diffs from git's own output and sends them as marked lines, so the clients need no diff algorithm. The AI and the user both change repositories in ways the server cannot watch cheaply, so the server announces its own git actions with a `GitChanged` event and clients also read the state again after file changes, after the AI stops working and after their own actions. Git actions are refused unless the workspace is Ready so they cannot race the AI's edits, and the server lets only one git action run per workspace. Squash, rebase and merge are workflows rather than single commands, so they live in their own server component that pushes after rewriting history, undoes everything when cancelled or crashed, and hands merge conflicts to the workspace's own AI instead of asking the user to edit conflict markers by hand.

## Client is dark only and view-model driven

The client forces the dark theme and takes its look from the Auto Dev app: VS Code style dark surfaces separated by thin borders, a blue accent, small corner radii, a drawer listing workspaces as a tree of groups, a header that turns blue while the AI works or git runs and a gear at the top right that opens the workspace's settings. A focused workspace is laid out for the device: the mobile client, for narrow touch screens, shows chat, files and scripts one at a time with equal tabs along the bottom, while the desktop and web clients have no bottom tabs and show the file system, the content of the selected file and the chat side by side with resizable separators, the file system much narrower (a seventh of the width) and the other two equal at first. The desktop client alone also has what only makes sense on a computer: a window without a title bar of its own, whose header carries the window controls, and buttons for the workspace folder in the file manager. A short ding plays when a workspace that was busy (AI working or git working) for at least two seconds becomes ready again, in any workspace opened this session, so a long task can be left alone; the delay keeps quick git refreshes silent. The tone is generated once (`ChimeSound`) and each head plays it with its platform's audio behind `IChime`: the Windows multimedia API or the first of `paplay`, `pw-play`, `aplay` and `afplay` on desktop, a notification-usage `AudioTrack` on Android, and Web Audio in the browser, which only plays once the page has had a click or key press. A client that gave a workspace work from its own chat, or whose bell button was turned on for it, also shows a "<workspace> is ready" notification when it is ready again (`IReadyNotifier`: an Android notification, a Windows toast or `notify-send`, a browser notification), and on Android an `IWorkKeeper` runs a foreground service while that work runs, because Android freezes background apps and a frozen connection would miss the end of the work and every event before it. The desktop window's title (in the window manager and task bar) is the open workspace's name, or the app's name when none is open. All clients use the Auto Dev app icon: the desktop window and executable, the Android launcher and the web client's favicon (embedded in `index.html` as a data URI to keep it a single file). These are the deliberate differences between the clients. Screens are plain Avalonia views bound to view models with no MVVM framework; the root view model decides which screen shows and owns the single server connection. Saved connection settings let the app reconnect on launch and only fall back to the host, port and access key screen when none are saved or the server cannot be reached.

## Workspaces are folders, AI sessions are attached to them

What the user manages is a workspace: a folder on the server. The AI conversation is a separate live AI session of the workspace's service that the server attaches to a workspace on demand and replaces silently when the service no longer has it, so a renamed folder or cleaned up data never leaves a workspace unusable. The groups the client shows in its drawer, which can contain other groups, are only a server-side grouping of workspaces, not a mirror of the file system. Everything about workspaces, groups, settings and conversations is stored on the server and the client keeps only how to reach the server, so any client sees the same state.

## All clients stay identical

The mobile, desktop and web clients are one product in three shells: a change to a screen, behavior or style lands in all of them together. Sharing `Client/Frontend/` makes that automatic for the two Avalonia clients (the git screens included); the web client is mirrored by hand. Files whose name ends in `.md` or `.markdown` are previewed rendered as markdown (headings, emphasis, lists and task lists, quotes, code, tables, rules) rather than as raw text. The Avalonia clients render it as native controls from a markdown parser, and the web client with a small built-in renderer since it has no dependencies; links are shown styled but are not followed, and images appear as their alt text. A `<br>` tag (also `<br/>` and `<br />`, in any case) breaks the line, in table cells too; other HTML tags are shown as text. A `mermaid` block in a file preview is drawn on request, by the server which makes the SVG. Other text files get syntax highlighting from a small built-in tokenizer rather than a grammar engine, so the clients stay dependency free and identical.

## The AI is trusted with unattended work

The server schedules what users give the AI (messages, queued inputs, loops, new sessions and delegations) and records what comes of it, but never judges or approves the work. It only holds work back when the user stops it or while the AI cannot run. The AI says itself when it cannot finish something, and whatever is not finished is told to its next turn.

## Local AI work is queued between whole pieces of work

One machine's models serve one session far better than several, so by default local work yields: it runs one piece at a time, the owner's before anything delegated. The server decides when a piece of work starts and never sits between the AI tool and the model server, which keeps every tool and model working as it does without Auto Remote, at the cost of not being able to share the model between sessions request by request. This is a setting rather than a rule because stronger hardware can serve several sessions at once.

## A swarm delegates tasks, not model requests

Servers share work as self-contained tasks (instructions and a git snapshot in, a commit and a report out) rather than by sharing models or sessions. A task survives slow and broken links and even a drive carried by hand, needs no shared files or credentials in the direct and air gapped modes, and its result can be reviewed before it touches anything. The price is that a worker knows only what the instructions say. Each pair of servers trusts each other by keys exchanged at pairing, not by the access key or TLS certificates, so a paired server gets to hand over tasks and nothing else, and what those tasks may do is decided on the machine that runs them.

## Scripts run on the server, beside everything else

A workspace's files live on the server, so its `.cs` scripts and `.task` files run there too: a client asks for a run and follows the output the server pushes, and the server keeps the runs so any client sees them. The AI and git actions both change the working tree, so the server enforces that a workspace is in exactly one state (Ready, Working or Managing) and that work only starts from Ready, instead of trusting each client to disable its buttons; the cost is that a git action cannot run while the AI works and the AI cannot be prompted during a git action. Scripts are deliberately outside that rule: they are the user's own processes, often long running and often wanted while the AI works, so any number run at once without locking anything.

## Ollama is started by the server when it can be

Ollama, which runs the local models, reads its settings (the type of its key and value cache, flash attention, how long a model load may stall) from environment variables when it starts, and its OpenAI compatible API cannot change them per request, so the server cannot set them in an Ollama that is already running. `OllamaService` therefore starts Ollama itself, as a child process that ends with the server, when the model server is an address on this machine and nothing answers there: before the first session of a local workspace and when the environment is saved with local models set. It always sets `OLLAMA_LOAD_TIMEOUT=0` (Ollama's default of five minutes fails the load of a large model on a slow machine with no explanation) and, with the Optimize context switch, `OLLAMA_KV_CACHE_TYPE=q4_0` and `OLLAMA_FLASH_ATTENTION=1`, which lets the same memory hold a context several times larger. Changing the switch restarts the Ollama it started; an Ollama it did not start is left alone and the environment's `localServerNote` says which variables its own service has to set, since silently running without them would only look like the setting not working. A model server that is not on this machine is never touched.

When the Ollama that answers is the systemd service `ollama.service` (the official Linux install, which runs as its own user), only root can change its variables, so `OllamaServiceUnit` offers that route: the server reports `ollamaServiceControl` (Linux with systemd, the unit exists, the model server is on a loopback address) and `ollamaServiceNeedsPassword` (`sudo -n true` fails), and the clients confirm a change of the Optimize context switch through `ConfigureOllamaService`. One `sudo` call runs a `sh -c` script with positional parameters that installs (or removes) the drop-in `zz-auto-remote.conf` under `/etc/systemd/system/ollama.service.d/`, runs `daemon-reload` and restarts the unit; the drop-in is a file of its own so removing it restores the service as it was and the user's own overrides are never edited. The password goes to `sudo -S -k -p ""` on its standard input only, never in the arguments, the environment or the logs, and the process runs with `LC_ALL=C` so the refusal can be recognized in its message (wrong password, no right to use `sudo`, or any other failure with its first line). `pkexec` and polkit are not used: they need a graphical agent a headless server does not have, and `systemctl restart` as a normal user waits for one. Before applying, the server stops an Ollama it started itself, and afterwards it waits until the service answers, so the clients get the stored environment only once it works.

# Usage

Runnable examples of `IAppInfo` in different situations.

## Read the product identity

```csharp
IAppInfo info = new IAppInfo.Factory().Create(typeof(Program).Assembly);
Console.WriteLine($"{info.Name} {info.Version}");
```

The version comes from the assembly, so a published build reports the release version it was built with.

## Run the server with a config file

`config.json` (or the path passed as the first argument):

```json
{
  "port": 52679,
  "key": "change-me",
  "dataFolder": "/home/you/.local/share/AutoRemote",
  "defaultFolder": "/home/you",
  "dotnetCommand": "dotnet"
}
```

```
Markwardt.AutoRemote.Server config.json
```

Only `key` is required; the other values shown are the defaults (`defaultFolder` defaults to the server user's home folder, and the example shows what that is on one machine). `port` (default 52679) is the one port every client connects to (secure WebSocket) and must be 1 to 65535, and the key non-empty, otherwise the server prints the problem and exits with code 1. `dataFolder` is where the server stores workspaces, the groups they are filed in (groups can contain groups) and the data of the AI sessions (a `liveai` folder); it is created when missing and defaults to the `AutoRemote` folder of the server user's application data. `defaultFolder` must be an existing folder: it is where a client starts when browsing for a new workspace's folder. The AI tools (their executables, API keys and local models) are not configured here but in the AI environment, which clients edit from the gear in the workspace list. `dotnetCommand` must resolve to the .NET SDK on the server's machine when scripts are run. Prompts never ask for permission, since they run unattended and cannot ask.

All connections are secure WebSockets (`wss`). The server presents the PFX named by `certificateFile` (with `certificatePassword` if it has one); without it, the server creates a self-signed certificate as `certificate.pfx` in the data folder on first start and prints its SHA-256 fingerprint on every start. A client connects to `port` and sends its access key as a JSON line. The server replies with a JSON line saying whether it was accepted, and keeps the connection open or closes it. Keys are compared in constant time, the line is limited to 1024 bytes, and a client has 5 seconds to send it.

The server writes a timestamped line to its console for each connection: when it arrives, when TLS is established, whether the client was accepted or why it was refused (wrong key, no handshake line within 5 seconds, a connection that closed or sent something else, no WebSocket upgrade), when it disconnects and how long it was connected, and any error that ended it. Keys are never logged. The clients log the same stages from their side (connecting, WebSocket and TLS established with the certificate fingerprint, accepted, or the stage that failed and why, and a lost connection) to the console: the terminal on desktop, logcat on Android (which `Scripts/Support/MobileClient.cs` streams) and the browser console on the web.

## Talk to the server from code

```csharp
IServerConnection.IFactory factory = new IServerConnection.Factory(new IMessageChannel.Factory(), new ConsoleLog());
await using IServerConnection connection = await factory.Connect(new ConnectionSettings { Host = "192.168.1.20", Port = 52679, AccessKey = "change-me" }, cancellation);

FolderListing start = await connection.ListFolders(null, cancellation);
FolderListing project = await connection.CreateFolder(start.Path, "my-project", cancellation);
WorkspaceInfo workspace = await connection.CreateWorkspace(project.Path, AiService.ClaudeCode, null, null, cancellation);
WorkspaceSettings settings = await connection.GetWorkspaceSettings(workspace.Id, cancellation);
await connection.SetWorkspaceSettings(workspace.Id, settings with { Capability = AiCapability.Strong, Effort = AiEffort.High }, cancellation);

WorkspaceGroup group = await connection.CreateGroup("Clients", null, cancellation);
WorkspaceGroup nested = await connection.CreateGroup("Acme", group.Id, cancellation);
await connection.MoveWorkspace(workspace.Id, nested.Id, cancellation);

connection.EventReceived += remoteEvent =>
{
    if (remoteEvent.Kind == RemoteEventKind.MessageAdded)
    {
        Console.WriteLine($"{remoteEvent.Message?.Role}: {remoteEvent.Message?.Text}");
    }
};

await connection.Prompt(workspace.Id, "Create a hello world program", cancellation);
await connection.Prompt(workspace.Id, "Make it print in French", cancellation);
ChatHistory newest = await connection.GetHistory(workspace.Id, null, 30, null, cancellation);
ChatHistory older = await connection.GetHistory(workspace.Id, newest.Older, 30, null, cancellation);
await connection.WatchWorkspace(workspace.Id, cancellation);
WorkspaceFiles files = await connection.ListFiles(workspace.Id, string.Empty, false, cancellation);
```

The workspace is named `my-project` after its folder, and the first prompt starts a live AI session attached to it. The groups only organize workspaces in Auto Remote and create nothing on disk. `Prompt` returns at once; the conversation arrives as events as the AI writes it, and a prompt sent while the AI is working is worked into that work (and asked again afterwards only if the AI did nothing about it). History is read in chunks, newest first. After `WatchWorkspace`, `FilesChanged` events report changes anywhere in the workspace folder, whoever makes them (the call replaces the workspace watched before). A refusal such as an unknown workspace throws `RemoteException`.

## Use the client app

The Android app (`Client/Mobile/`) and the desktop app (`Client/Desktop/`, a window without a title bar of its own that opens maximized and runs on Windows and Linux) are the same client and use the same port as the web client; the desktop app keeps its settings in the user's application data unless started with `--data-folder <path>`. Everything below applies to both.

1. On first launch, enter the server's host, port and access key. They are saved on the device, the client accepts whatever certificate the server presents, and later launches reconnect straight to the workspaces (a server that does not answer, for example while it restarts, is retried for two minutes before the connect screen is left to the user). The desktop client also shows a Connect to Local Server button for each server on the same machine that allows the account running the client (the server's `localUsers`, regular user accounts by default); it is remembered without the key and asks the server again at every start. If the connection is lost, for example while the app was in the background, the client reconnects by itself, shows "(reconnecting…)" after the workspace name meanwhile and then reads what it missed, so messages posted in the meantime appear. Everything else, the workspaces, groups, settings and conversations, lives on the server.
2. The menu button opens the drawer listing workspaces and groups as a tree. The client always opens with no workspace focused and the drawer open. The list scrolls on its own when it has more rows than fit (the filter box and the buttons below stay in place), on a touch screen a drag that starts on a row or on one of its buttons scrolls it and only a tap presses a button, and the list keeps its scroll position and the open workspace's highlight when it updates, for example when a workspace is added from another client. A filter box at the top narrows the list as you type: a workspace shows when its name or folder contains the text (ignoring case), together with the groups holding it, and a group whose name matches shows with everything in it; groups are all open while a filter is set, and the filter only changes what is shown. Tap a workspace to focus it, tap a group to expand or collapse it; groups start collapsed, and the groups holding a workspace that gets focused (from a notification, or after creating it) open so that it shows. At the top level and inside each group the groups come first, in a custom order that is the same on every client (up and down buttons, the triangles, move a group one place among its siblings, and new groups go to the end), and the workspaces follow. A workspace that is working (the AI works or git runs, in any of its sessions, as when the header is blue) is highlighted in that blue and comes before the others of its group, and a highlighted one that is focused has a white bar on its left edge. A group holding a working workspace, however deep, is highlighted the same way, open or closed, so work inside a closed group still shows; groups keep their custom order. Next come the ones a loop of the AI runs in, each with a loop icon next to its name (working or not), then the rest. Within each of these the one whose AI session was loaded most recently is first (workspaces have no manual order), and rows move as work and loops start and end, on every client. A group has buttons to rename it (pencil), move it (arrow) and delete it (cross); a workspace has a move button. Moving asks for the group to put it in, or the top level; a group cannot go into itself or anything inside it. Deleting a group keeps what is in it and moves that up a level. The gear at the top right of the drawer, plain like the other top bar buttons, opens the AI environment settings. New Workspace, Clone Workspace, New Group, Swarm and Change Server are at the bottom, all alike; New Group asks where to create the group (the top level or any group) with a dropdown. Button text is capitalized like this throughout the app.
3. A new workspace is a folder on the server: browse from the server's default folder, create folders as needed, then start the workspace in the folder you are viewing. The workspace takes the folder's name. Cloning is the same screen with a repository URL and an optional folder name added: the server clones the repository into a new folder inside the folder you pick and starts a workspace in it. Both screens also choose the AI provider the workspace runs on for good (Claude Code, OpenAI Codex or local models, starting with the default of the AI environment) and, for Claude Code and Codex, take an optional API key that is used for just that workspace's session. Both screens also have a dropdown for the group the workspace is filed in (the top level or any group). Groups in the drawer are different: they only organize workspaces in Auto Remote and are not created on the server's disk.
4. A focused workspace has a gear at the top right that opens its settings (press it again to go back): the provider (shown only: it is fixed when the workspace is created) and everything the AI session is configured with: capability, effort, the Sandbox switch (off by default: on, the AI has no shell and no files outside the workspace except what Auto Remote shares with it) and switches for the web, image generation and letting the AI delegate work, the standing instructions, the status interval of the workspace (empty uses the global one, shown as the hint, with a clear button) and the review and expand prompts of the workspace (empty uses the global ones, which show as the hint, and a clear button empties the field) and the lines the session writes about how it runs, such as the model it chose. The settings are sorted into collapsible sections (AI, Access, Instructions and prompts, Side sessions, How it runs, Errors, and Workspace for the buttons below; a side session shows neither Side sessions nor Workspace), all collapsed when the panel opens, in a column of limited width centered in the window like the AI environment settings, which are sorted the same way (New workspaces, Status and prompts, Claude Code, OpenAI Codex, Local models, Image generation and, in the apps, Updates). The Errors section lists the errors the AI of this workspace ended with in the last 30 days, newest first with the time of each (the server keeps them and removes older ones), or says there are none; it only ever shows errors of this workspace. Nothing is saved as you edit: the changes are pending and are sent together when the settings are closed (the gear again, another tab, another workspace, or the move button); when the server refuses them the settings stay open with the reason. In the Workspace section are Rename workspace, which renames the workspace's folder, Move workspace to folder, which opens a folder browser (starting in the folder the workspace is in, or the default folder when that is gone) to pick the existing folder the workspace works in from now on with a Use this folder button, which only tells the AI session (no files are moved, so move the project there first when it should go along), and Delete workspace; the drawer's own move button is different, it files a workspace into a group. The gear at the top right of the drawer opens the AI environment: the default provider for new workspaces, what the AI session of a new workspace starts with (capability, effort, the same switches and the instructions as the workspace settings, which a workspace then keeps and changes on its own), the status interval in minutes (default 5) the AI is told to report its status at in every workspace without one of its own, and the review and expand prompts the message box buttons send in every workspace without prompts of its own (empty restores the default), the executables, configuration folders and API keys of the tools, the max usage window limit in percent (default 95) in the section of each provider that reports usage windows (Claude Code and OpenAI Codex, not the local models), at which the AI is told to pause its work in every workspace that uses it while a usage window of that provider is at or past it (the server checks again every 15 minutes and tells the AI to resume once no window is), the local model server with a model and a context size (its own full-width field under the model, in tokens) for each capability, an Ollama command and an Optimize context switch (Auto Remote starts Ollama itself when the model server is on this machine and is not running, always with no limit on how long a model load may stall, and with the switch on also with a quantized q4_0 key and value cache and flash attention, so the same memory holds a much larger context; a note under the switch says whether Auto Remote started Ollama or it already runs outside Auto Remote, where these variables have to be set in its own service; when that Ollama is the systemd service `ollama.service` of a Linux server, turning the switch on or off opens a dialog that explains the change and, only when `sudo` on the server needs one, asks for the password of the account the server runs as: the server then adds or removes a systemd drop-in with the variables and restarts the service, so its loaded models are unloaded for a moment, and a wrong password is shown in the dialog, which Cancel closes while putting the switch back) and the image generation service, each with a button that reads the available models or checkpoints from their server again. It has no save button either: its Close button sends what was changed (nothing is sent when nothing was), and the screen stays open, showing why, when the server refuses it. The mobile client shows chat, files, scripts and activity as tabs along the bottom, plus a History tab when the workspace is a git repository; the desktop and web clients have no bottom tabs and show the file system, the content of the selected file and the chat as three panels side by side with draggable separators between them (a thin line, with a wider invisible grip), the file system much narrower (a seventh of the width) and the other two equal at first. The chat panel has its own tabs, as in Auto Dev: an underlined tab for the one showing, Chat, Script, Activity and History (when the workspace is a git repository) in the desktop and web clients. The desktop client has a button for a new window right of the workspaces button in the top bar, which starts another instance of the app as a process of its own (with the same command line, so the same data folder), for watching two workspaces at once. The message box has no background or border, only buttons beside it (in the desktop and web clients Enter starts a new line, Shift+Enter does what the send button does and Alt+Enter queues; sending an empty box does nothing): the send button whenever something is typed or attached, which sends at once, or opens Send Options while the chat takes nothing at once (while git works, or while work is being stopped or cancelled), and while the box is empty a review button, an action button like send and stop (a square with a background and border; blue because it sends at once), which sends the review prompt as the user's prompt (it is available in Ready and Working and refused while git runs). An expand button of the same shape sits right of it, shows in the same states and sends the expand prompt. Both prompts are set in the global settings (by default "review workspace and fix any problems or inconsistencies" and "expand upon content in workspace in areas that make sense"), and a workspace can override either in its own settings, where clearing the field (or its clear button) uses the global one again; the buttons read the prompts from the server when pressed. Beside them sit a pause button and a resume button, shaped and coloured like it, which send "pause current work" and "resume unfinished work" to the AI as the user's prompt (pause shows only while the AI works and the box is empty, so it steers the running work; resume only while the workspace is ready and the box is empty). Sending this way never turns on auto commit. Send Options has no button of its own: right-click the send, review or expand button (the menu key works too), or hold a finger on it on a touch screen, which sends nothing and opens the options. They start by showing what they submit, which cannot be changed there and follows from the button: Custom (what is typed and attached) from the send button, or the Review or Expand prompt from its button. They choose When (Now, Next to queue it, or Repeat), Where (This Chat or New Session, which only Now offers) and, as When Done, what happens afterwards, as items 7 and 17 to 22 describe. In this chat of a git repository When Done is Commit or Keep Changes for each of Now, Next and Repeat; it starts as Keep Changes for Now and Repeat and as Commit for Next (Keep Changes for a loaded draft with its commit off). Now with Keep Changes leaves the commit of work it joins as it is, and the options say when that work commits anyway. They open on Now. What cannot be chosen is disabled, with the reason: while the chat takes nothing at once they open on Next, and Now then only leads to a new session; Repeat needs no running loop and, apart from a commit that follows work, a chat that takes input; attached files can only go to this chat, Now or Next. Enter goes ahead with what is chosen and Escape cancels (in a box with several lines Shift+Enter starts a new line, and on the mobile client and touch screens Enter does too). Repeat sets up a loop that sends what the options submit over and over, with the minutes between runs (0, or an empty box, runs again as soon as a run is done), when it ends by itself (never, at a time of day, after a length of time, after a number of runs, or when a usage window reaches a share of its limit, offered when the service reports windows); with Commit as When Done every run is committed. While a loop runs a loop icon shows beside the workspace title in the header (its tooltip says what it sends, how often, when it ends and how many runs it made; clicking it shows, counting down, when the next automatic prompt is sent; while the loop runs, a workspace that becomes ready again plays no sound and sends no notification, and one that is waited for with the ready notification sends it once the loop has ended) and the message box shows a Cancel Loop button, which ends the loop but lets the run in progress finish. A run that fails never ends the loop, and while the AI cannot run the loop waits and tries again by itself. Stop does not end it: it is held until Resume. When it ends by itself a note under the conversation says why. A loop goes on after the server restarts. While the AI of a workspace is paused automatically because a usage window reached the max usage window limit of its provider, the status line above the conversation says so with a Cancel Auto Resume button, an amber pause icon shows beside the workspace title, and nothing that runs by itself is sent; both go away when the AI is told to resume. Cancel Auto Resume ends the pause without resuming the work, and what runs by itself in the chat then waits for Resume. Sending input while a window is at or past the limit, or while the workspace is paused, first opens a popup (Over the usage limit) that names the window and asks whether to start the work anyway: Start Anyway sends the input and the workspace ignores the limit until that work is done, Cancel sends nothing and keeps what was typed (the pause button needs no confirmation). While the AI works and the box is empty the stop button joins the others, and the review and expand buttons stay, so their prompts can be sent as mid-turn input to the work in progress like anything typed; Send Options opens from them too (a loop started while the AI works waits until the work is done before it sends its first prompt), and Cancel Loop stays beside them. While something is typed during work, a note says that Send joins the running work. On the desktop and web clients it starts taller, its height can be dragged to anything by its top edge (even shorter than the text), and typing grows it just enough to show the text when it is too short (leaving space for the conversation); once it is empty again, for example after sending, it returns to the height it had before it grew. A microphone button beside the paperclip starts voice input in every client: it switches to a full screen of its own that starts recording at once, with a running time and a Complete and a Cancel button (Cancel throws the recording away; the recording also ends by itself after a minute, the longest, as if Complete was pressed). Complete sends the recording to the server and opens the drafts, where a special entry shows the speech being turned into text (by the Whisper model built into the server, or the `speechCommand` set in its config), with a Cancel button that stops it and removes the entry. When the text is ready it fills the entry, which is then a draft like any other that can be picked to put the text into the message box, where it can be edited before sending. Since the server keeps the entry, the user can leave the list, the workspace or the client meanwhile and every client shows the same entry. When the conversion fails (nothing was heard, voice input is turned off or the model cannot be loaded) the entry shows the reason until it is dismissed. The button is unavailable while the box is blocked by git or while a finished recording is being sent, and the box shows the reason when the microphone or the permission (Android asks the first time) is missing. The desktop client records with `parecord` or `arecord` on Linux and the Windows multimedia API on Windows, Android through its audio recorder and the web client through the browser (which asks for the microphone and needs a secure page or `localhost`). Files and images are attached by pasting them (Ctrl+V; a copied image or copied files) or with the paperclip button beside the box; they show as removable chips above the box and are sent with the next message (up to 20 MB each), which tells the AI where to read them (the AI can always read, but not change, the attachments of its own workspace, also when it may not access other files outside the workspace). In the conversation a sent message shows its text with the attached files as named chips below it (hover for the server path), not as raw `Attached file:` lines; the clients recognize those trailing lines in the stored prompt, so older history displays the same way. What is typed in a workspace's message box is kept on the device per workspace (in a file beside the saved connection settings in the Avalonia clients, in the browser's local storage in the web client), so unsent text comes back after the app or tab was closed, and it is cleared once sent. A client can show a notification saying "<workspace> is ready" once a workspace is ready again. A prompt sent or queued from the client's own chat, or Resume, turns it on by itself (work started from another client or a script does not; one that fails leaves the bell as it was, and off when nothing is left to wait for), and a bell button beside the title turns it on or off: it shows while the focused workspace or side session has work that is not over (it works, a git action runs, a loop runs, work waits for the local AI or tasks its AI delegated are under way) or its notification is on, and is filled while the notification is on. Use it to be told about work that is already running, such as work another client started or that was running when the app was opened, or to stop being told. It applies to that client alone, speaks once and is not kept when the app is closed. Each workspace has its own notification, which is withdrawn again as soon as the workspace works again, so a workspace never shows as ready while it is working (the ongoing notification of the foreground service on mobile only names workspaces that are working), and opening it brings that workspace to the front (on mobile also when the app has to start first, in which case the workspace opens as soon as the app is connected; in the browser clicking the notification focuses the page and the workspace; on the desktop client clicking it restores and raises the window and opens the workspace, where the window manager allows a window to take focus and the notification server supports actions). It is an Android notification on mobile, a Windows toast or a `notify-send` notification on the desktop client (nothing when `notify-send` is missing; its process is ended after 10 minutes, when a newer notification of the same workspace replaces it, and when the app exits, since a notification server may never tell it that the notification went away), and a browser notification in the web client, which asks for permission the first time you send a prompt or press the bell and only works while the page is open (where the browser blocks it, pressing the bell says so, and where the browser has no notifications the bell is not shown). Android stops apps in the background, so while mobile work runs the app is kept connected by a foreground service whose ongoing notification names the workspaces working; it ends when they are ready again (after a prompt whose AI delegated tasks, once they ended and the AI dealt with them), and after twelve hours at the latest. Android may ask once to allow notifications. Text in the chat, the file preview and the script output can be selected with a mouse, or on a touch screen only by holding a finger still on a word for half a second (which selects it, and dragging then extends the selection); a touch that moves first is a scroll, and tapping or double tapping never selects, so touching text to scroll does not highlight it. Touching any such text drops the selection a hold made. Chat is a live conversation: every message carries the time it was written, shown small and muted under it in the local time zone (the time of day for today, "Yesterday" with it for yesterday, the abbreviated month and day for the rest of the year, the whole date for earlier years; hovering shows the full date and time; left aligned in your own messages and under the AI's), the AI's messages appear as it writes them, rendered as markdown (your own messages stay plain text), you can keep sending messages while it works and they join that work, and only the newest chunk loads when a workspace opens. What you send shows in the chat at once, marked Sending… until the server has taken it (which can take a few seconds); if it cannot be sent it leaves the chat and goes back into the box. The chat keeps a short window of messages so a long conversation stays fast: older ones load, a chunk at a time (a chunk is the messages that fit in about 20,000 characters of text, at most 100, so a few long messages and many short tool lines weigh the same, and the work of the AI counts when it is shown), only when you scroll up to the top yourself (scrolling, the scrollbar or the wheel; a chat that is not at the top never loads by itself); the chunks loaded that way are dropped again when you scroll back to the bottom or turn auto scroll on, and while auto scroll follows new messages the oldest are dropped as new ones arrive so the window stays at one chunk. What was dropped loads again when you scroll up to it. With auto scroll on you can still scroll up as far as the chat goes: only new output takes you back to the bottom, never older messages loading, text wrapping anew or the chat being read again after a lost connection. When the AI fails, an error line under the conversation shows the time of the failure above the reason, in every client looking at the workspace, and goes away in all of them with the next message sent from any client. Files shows the workspace folder as a tree like the Auto Dev app, names only: tap a folder to open or close it in place (a button closes every folder) and tap a file to preview it. On mobile, double-tap a folder to make it the root of the tree; the desktop and web trees always start at the workspace folder. None shows the root path or an up button. The desktop and web trees keep the file being previewed selected, and open the folders above it when the previewed file (or diff) changes, but never again after that: any folder can be collapsed by hand, also one that holds the previewed file (which then shows no selection until it is visible again), and reading the same file again leaves the folders as they are, and offer Copy Name, Copy Relative Path and Copy Absolute Path when a file or folder is right clicked (a right click never opens or closes a folder). A `.filehide` file, in the workspace folder or any folder inside it, hides files and folders from the tree. It uses the `.gitignore` format (comments, `!` to show again, a trailing `/` for folders only, `*`, `?`, `[...]`, `**`, and patterns with a `/` anchored to the file's folder), applies to its folder and everything below, and hides everything inside a hidden folder. A magnifier button at the top of the file system swaps the tree for a search, as in Auto Dev: type to find files by name (fuzzy, best match first, at most 50), or tick Search file contents to list the lines of text files that contain the text (at most 200, ignoring case) with their file and line number. Searches skip `.git` and what `.filehide` hides (unless See hidden files is on). Choosing a hit closes the search and previews the file; a line hit also opens the find bar with the text and moves to that line. The eye button next to Collapse All turns See hidden files on to show them again; it is off by default. The tree updates by itself when anything in the workspace folder changes, whoever changes it (the AI, a script or another program outside Auto Remote), and so do the git colors and, for a file that is open, its content (read again at most once every few seconds). A previewed file has a bar on top like Auto Dev's editor: back and forward buttons that step through the files and diffs opened since the preview was last empty, as a browser's do (up to 100; opening something new after going back drops what was ahead, and closing the preview forgets the steps), a label saying whether it is a file or a diff, its path, a find button, a word wrap button (not for rendered markdown, which has the collapse all button there instead) and a button that closes it. The text sits straight on the panel background. A markdown file (`.md`, `.markdown`) is shown rendered, with a chevron beside each heading that folds away what is under it up to the next heading of the same or a higher level (so a heading's subheadings fold with it), and a button in the bar above that collapses every heading, or expands them all when they are all collapsed; a find that navigates to a match inside a folded section opens the folds around it, and folds stay as they are while the file is searched but start open again for another file or changed text (chat messages are not foldable). The nesting of the sections is drawn too: a section's content is indented, by less at every level, behind a thin guide line at its left edge that lights up while the pointer is over its heading; headings get lighter and dimmer with each level, and those of levels 1 and 2 have a hairline under them. A fenced block tagged `mermaid` shows as a Show Diagram button; pressing it draws the diagram (the server does the drawing), sideways scrollable when wide and zoomable (buttons above it, or Ctrl and the mouse wheel), and a diagram that cannot be drawn shows the reason and its text. Three more buttons in the bar act on the headings: one numbers the sections (1, 1.1, 1.2 and so on, shown faintly before each heading; when the document has a single heading of the top level, its title, the sections are numbered under it; it is off by default, and turning it on is remembered for that file in that workspace on the device, in a preferences file beside the saved connection settings in the Avalonia clients and in the browser's local storage in the web client, so the file comes back numbered and every other file starts unnumbered; turning it off forgets it), one folds the document to a nesting level (the headings down to the level show and everything under them is hidden, or All opens everything), and one lists the outline, every heading indented by its nesting, where choosing one opens the sections around it and scrolls to it. While the preview is scrolled, a breadcrumb bar over its top names the headings the top is under, outermost first (Handbook, Part 1, Chapter 1.2), and choosing one scrolls to it; it is gone at the very top. None of this applies to the chat, and a file that is not markdown is never rendered as markdown; other files are shown as monospaced text with line numbers (long lines scroll sideways, or wrap with the word wrap button and keep one number per line; the text and a diff scroll both ways from anywhere in them, the sideways bar always sits at the bottom of the panel rather than the end of the file, and the line numbers stay in place while scrolling sideways), colored by syntax when the language is recognized (for example C#, JSON, YAML, XML and project files, JavaScript, TypeScript, Python, shell, SQL, CSS, HTML, INI, `.env`, CSV and Dockerfiles). Every previewed file, rendered markdown included, has a find bar (the magnifier button or Ctrl+F) with a match count, match case and whole word options, and next and previous match (Enter and Shift+Enter) that marks the matches in the text; in rendered markdown it searches the text as shown (formatting characters are not part of it) and a line hit from file search only opens the bar. On the desktop and web clients the message box grows with its lines of text, centered vertically in the box, until it fills it. The file system's buttons sit at the right of its header. Rename renames the workspace's folder on the server. Delete removes the workspace, and by default its folder and everything in it; untick the box to keep the folder. Its side sessions and their changes are deleted either way.
5. A workspace whose folder is a git repository shows its git state, and every git action runs on the server. At the top of the file system sits the version section: the branch (or the tag or a note when the head is not on a branch), a tag at the head, the head commit's message and abbreviated hash, and an asterisk with a highlighted background while there are uncommitted changes; like in Auto Dev it is plain until hovered, with a line under it. The questions it asks (a commit message, a branch name, the remote URL and so on) open with their box focused and ready to type; Escape cancels and Enter submits (Enter does not answer a question that destroys work, such as a reset, which only its button does), and on a touch keyboard the text starts with a capital letter, except for a URL or an email. Tapping it offers Commit (stages everything, asks for a message and pushes the branch when there is a remote), Auto Commit (has the AI write a commit message of eight words or less for the pending changes, then commits with it like Commit does), Reset (discards every uncommitted change after a confirmation), Branch (creates a branch at the head, checks it out and pushes it), Tag (annotated, pushed) and Remote. The first time a commit, tag or history rewrite needs it and git does not know who you are, the client asks for a name and email and saves them in the server user's global git configuration. The files in the tree are colored like Auto Dev: new files green, changed files and the folders containing changes yellow, ignored files and folders dim. The changes button next to Collapse All switches the tree to Changes Mode, a tree of only the changed files (deleted ones in red); tapping a file there shows its diff in the content panel, the whole file with added and removed lines marked and the line numbers before and after. The History tab draws the commits of every branch newest first the way the Git Graph extension of VS Code does: a graph on the left with a colored line for each branch that is open and a dot per commit, curves where branches split and merge, the branch and tag badges in the color of their line next to the subject (a local branch and its remote copy on the same commit share one badge), and the author, date with time and abbreviated hash on the right of each one line row, with the full hash as its tooltip; tapping a commit lists the files it changed as a tree, with the graph carrying on beside it, and tapping one of those shows its diff in the content panel. Older commits load on request, and a Fetch button next to Refresh fetches the remote. Right clicking a commit offers Checkout (a plain commit, which detaches the head), and right clicking a branch or tag badge opens its menu: Checkout (changes that are not committed are discarded after a confirmation that says so), Squash, Rebase and Merge between the badge's branch and the checked out branch in either direction, and Delete (locally and on the remote, after a confirmation). Squash and a rebase or merge of a branch with several commits ask for the message of the one commit that replaces them, defaulting to the tip's message; rebase and merge need a clean working tree and tell you when there is nothing to do. A rebase or merge that conflicts is handed to the workspace's AI: nothing blocks the screen: a workspace is Ready (nothing runs), Working (the AI runs) or Managing (git runs), and it only leaves Ready for one of them, so git actions, rename and delete wait until it is Ready again, and more AI input is only taken while Ready or Working. While the work in a workspace runs (the AI or git), the empty message box shows work buttons. While the AI works the button is Stop (ends the work at once and keeps what it did; the AI is told it was interrupted and a loop ends with it). Stop is also there while git works (stopping git undoes the action), and while the server is cancelling work on request of another program (disabled then); the clients have no button that reverts the AI's work. Stop asks "are you sure" first, and the workspace is Stopping meanwhile, locked like any other busy state. Once something is typed the send button shows, so more input can still be given. While git is working on the server (from any client) the workspace shows it like it does while the AI works (the top bar turns blue), nothing is sent at once, with a hint saying git is working (the send button opens Send Options), and a bar above the message box offers Cancel and undo; the chat shows what the AI was asked and does, and when it cannot resolve the conflicts everything is put back and you are told. A merge fast-forwards the target, pushes it and deletes the merged branch everywhere. While a workspace is focused its checked out branch is fetched and pulled every minute and whenever the history opens (changes that are not committed are stashed and restored around the pull, with the AI resolving conflicts of the restore). Everything refreshes by itself when files change and when the AI finishes working. Commit, Auto Commit, Reset and Branch are refused while the AI is working in the workspace. The popup that asks for a commit message, branch name or a confirmation closes as soon as it is submitted while the action runs (the workspace shows git as working); if the action fails, the popup returns with what was typed and the error.
6. A git remote icon sits in the toolbar of the history panel, left of fetch and refresh: it sets the `origin` remote of the workspace, turning a folder that is not a repository into one first, or repoints the remote of an existing repository (the field starts with the current URL).
7. While text is typed the message box offers Save Draft, which keeps the text as a draft of the workspace on the server and clears the box. While the box is empty the Drafts button, the first of the buttons beside the box, opens the drafts (it has a blue border while there is one) as a list that covers the whole chat, the last saved first; picking one removes it from the list and puts it into the message box. Each draft has a delete button, which asks first, in a git repository a commit button for when it is queued (on by default), and Run in New Session, which starts a new side session on it that runs at once beside the current work and is brought back when done. Every client sees the same drafts.
8. While the AI is working or git is running in the focused workspace, the header bar with the workspace title turns blue, on every tab and in every layout.
9. Next to the gear is a usage icon, colored by how fast the shortest usage window of the workspace's AI service is being used: green when well under an even pace, blue when under, the normal color when even, orange when over and red when well over or used up. Tapping it lists every window the service reports (such as session, week or a per-model week) with how much is used, its pace color and its reset time. The server reads them through Live AI from the service's own report, reuses a result for just under a minute, and clients ask once a minute and again as soon as they reconnect, so a lost connection does not leave old numbers behind; a window that already reset shows 0%.
10. Only the desktop client has a window without a title bar: the header is the title bar (drag it, double click to maximize) and minimize, maximize and close buttons sit to the right of the gear, all the same size and evenly spaced with the other top right buttons. Its file system also has buttons that open the workspace folder in the file manager (when the folder exists on the machine the client runs on, which is the case when the server runs there too) and copy the workspace folder's path.
11. Every client runs `.cs` single-file scripts and `.task` files on the server. They show with a play icon in the file system and run when double clicked on a computer or long tapped on a touch screen (mobile, and the web client on a touch device, where a double tap does nothing); the Script tab, between Chat and History on the desktop and web clients and between Files and History along the bottom on mobile, opens. Its dropdown lists the runs (running ones with a dot; a finished one can be removed), a task shows one sub tab per script, and the output of the chosen script appears live in a monospaced view with its state, a button that copies all of it and, while running, a Stop button (a whole task stops) and a box that sends a line to the script's input. Any number of scripts and tasks run at once, beside each other and beside the AI and git: a running script never locks the workspace, so the AI can be prompted and more scripts started meanwhile (a file that is already running cannot start twice), and the Stop of the message box ends the AI or git, not scripts. The server keeps the runs, so they are still there after the client reconnects.
12. The chat and the script output each have an auto scroll toggle (a double arrow button: at the bottom right of the chat, and in the script's header beside Copy). Both start on, and while one is on its log jumps to the bottom whenever new content arrives; turn it off to read earlier output while more arrives. The two are independent and are not remembered between sessions. Next to the chat's auto scroll button is a button with a terminal prompt icon that shows the work of the AI in dimmed text between its messages: what it reasoned (with the time it started), and each tool it used as a short line ("Read src/Program.cs", "Run dotnet build", "Write notes.md (12 lines)") followed by a short result ("→ 120 lines", "→ Failed: no such file"), never the content of a file or the whole output of a command; it is off by default, the server remembers it for the workspace and every client follows it, and while it is on the AI's answer and its reasoning are also streamed, growing in the chat as they are written (the reasoning is kept as a message of its own when it ends, with its time, so it is still there when the work is turned off and on again), and the global AI settings choose what new workspaces start with ("Show the work of the AI in the chat" under New workspaces). On a touch screen, holding a finger on text in the chat selects the word under it (the same goes for the other long texts, such as file contents and script output). Drag on without lifting, or drag the handle at either end, to stretch the selection; it crosses the paragraphs, lists, tables and code of one message but not into another message, and dragging to the top or bottom edge scrolls on. A bar by the selection has Copy and Select All (the whole message). Scrolling keeps the selection and a tap anywhere else drops it. The web client uses the browser's own text selection.
13. When GitHub has a release newer than the client or its server, an update icon appears next to the menu button. Pressing it asks for confirmation; confirming switches to an updating screen that follows the update while the server is updated first (it restarts) and then the client, which installs the release in place of itself (the desktop app restarts, Android hands the package to its installer). The updating screen stays, also in the restarted app, until the server answers again, and the connect screen with the failure only appears when it has not for ten minutes after the downloads were complete. Whenever the client connects and its version differs from the server's, the workspaces are replaced by a screen that only offers Update, when a newer release exists, or Change server. The global settings also have a Check for updates button, with the versions of the app and the server and an Update button when something newer exists, for looking up a release without waiting for the next automatic check. The web client has no update system.
14. The AI is told to write a short status update as a normal chat message while it works, at the interval set in the settings (5 minutes by default, per workspace if overridden), so the chat does not go quiet during a long run. It runs long work in the background (background commands and helpers, followed with wait, output and stop tools) so it can keep reporting meanwhile, but it must keep its turn open and wait for all of it before giving its final reply.
15. A server that runs local models can usually serve one AI session well and two badly, so work of local model workspaces can wait in a queue (Claude Code and Codex work always starts at once). Under Local models in the AI environment, When busy chooses Yield (the default: one local AI session at a time across all workspaces, running work finishes first, and your own work starts before delegated tasks) or Simultaneous (everything starts at once, and Delegated tasks at once, 1 by default, limits only the work other servers delegate). A prompt that has to wait shows in the status line above the conversation with its place in line, and the drawer marks the workspace Waiting for Local AI; further messages join the waiting prompt. Cancel Waiting Work removes it: a prompt sent from that client goes back into the message box above anything typed there, with its attachments, and one sent from elsewhere is kept as a draft. Waiting work starts against the files as they are then, sends no ready notification while it waits (also when the input was queued) and is still waiting after a server restart. The commit message of Auto Commit, the AI resolving conflicts and each run of a loop wait their turn too.
16. A swarm lets servers on different machines hand each other work, mainly to spread it across local models. The Swarm button below the workspace list opens its screen on the server you are connected to.
    - Pairing connects two servers and turns nothing on. Over a network (a trusted LAN, or the internet through a VPN or a reachable port), use Create Pairing Code on one and enter its address (`host:port`) and the code under Pair with Code on the other; the code works once, for 15 minutes. Without a network, set the drive folder (a folder on the server's machine where the USB drive is mounted), use Write Drive Invitation, carry the drive to the other server and press Sync Drive there, confirm the invitation, then bring the drive back, Sync Drive and confirm the acceptance. Compare the fingerprints before confirming. The clocks of paired servers must agree within 15 minutes to connect.
    - For each paired server choose a Delivery mode on both sides: Git remote (code travels as `swarm/` branches of the project's `origin`, which both servers must be able to reach with their own git credentials; a worker only does this while its own mode for the sender is Git remote too), Direct (code travels over the connection as git bundles) or Air gapped (everything travels on the drive, moved by pressing Sync Drive on each side). For the first two, enter the other server's address on whichever side can reach the other.
    - On the server that delegates, turn on Send work to this server. On the one that does the work, turn on Accept delegated work (under This server) and Accept work from this server, and set what that sender's tasks may do: the Sandbox, the web and image generation. The Sandbox is off at first, so an accepted task has a shell and can reach everything the server's account can; accept work only from a server you trust that much, ideally on a server running under its own account, or turn its Sandbox on, which leaves it reading and editing files without building or testing them. Delegated tasks run only on local models, so set them up for each capability the worker should take, along with the tools and package caches the tasks need. Once a server has run a delegated task, OpenCode ignores the project level configuration (plugins and MCP servers) of every workspace on it until the server restarts.
    - Delegate a task by hand by choosing New Session in Send Options and a server under Run On: a title, instructions (what the options submit) that are complete on their own (the worker sees nothing of your conversation and cannot ask), optionally the expected result, the capability, and whether the result is brought in by itself (Bring Into Main, the default) or kept separate. It needs a workspace whose folder is the root of a git repository with a commit, and starts from the current files, uncommitted changes included and ignored files left out.
    - For the AI to delegate, turn on Let the AI delegate work in the workspace's settings, under Access (the AI environment sets what new workspaces start with; both start off). It then decides what to hand out without asking about each task and ends its turn, which is committed if set to. Once every task of the job has ended, the AI gets a turn of its own with the results, brings in what it wants and confirms it, and deals with failed or lost tasks. The chat's queued inputs and loop wait for that; bringing in other work does not.
    - Delegated tasks show in the Sessions list of the chat that delegated them, under Delegated Tasks, in the drawer and on the Swarm screen. A task opens to its instructions, report and conversation, which grows live over a network, with Bring Into Main (or into the side session it came from), Continue Here (makes a side session from the result to go on with by hand), a When Done switch, Retry Task, Cancel Task and Discard Task. The AI brings results in, using git or editing files as it sees fit; a task is removed once its AI confirms it, and one it could not bring in stays, marked Needs attention. A task that builds on others gets their results beside its code and combines them itself. A task whose worker has not been heard from for three minutes is Lost; it is not moved elsewhere on its own. The ready notification of a prompt waits while delegated tasks it waits for are under way (on mobile the app stays kept alive meanwhile), and tasks kept separate send their own notification when they end.
    - A server running a task shows it as a workspace marked "Delegated by ...", which can be watched, stopped or deleted (the sender is told) but takes no messages, settings, renames, moves, loops, git actions, side sessions or scripts: the message box, Send Options and its settings are disabled, its script files cannot be run, and Stop cancels the task. It is removed once the sender has the result.
    - Revoke Server ends the pairing and the tasks between the two.
17. A workspace whose folder is the top folder of a git repository with a commit can be worked by several AI sessions at once. Tap the title to list them: Main comes first, then side sessions and delegated tasks. Sessions are started from the message box (the list has no button for it): choosing New Session under Where in Send Options makes a side session with a name, its starting files (Current Commit, or Current Files with what is not committed), what the options submit as its first task, and When Done: Bring Into Main (the default) or Keep Separate. A side session has its own files, chat, scripts and loops, its AI knows what main's AI had finished by then, and the header reads `workspace / session` with a Side marker. Switch by choosing a row. The `⋯` button of a side session has Bring Into Main, the When Done switch, Changes Since Session Start (also a button above the file tree), Rename and Delete.
    - Bring Into Main has main's AI bring the session's work into main in a turn of its own, using git or editing files as it sees fit; every session ready at the same time comes in one turn, and the AI decides how to combine them. Its changes are committed afterwards unless that is turned off in Up Next. The session is removed once the AI confirms it, with no approval step and no undo, and its report and changed files stay in main's Activity. A session set to Bring Into Main when done comes in by itself once its work ends well with nothing left to run. One the AI does not confirm after two turns is given back as it was, marked as needing attention. While a session is being brought in it cannot be opened and its row offers Cancel Bring In, which gives it back without undoing anything main's AI already changed.
    - Git in a side session shows history and changes, commits (never pushed) and discards; branches, tags, remotes, merging and rebasing are done in main.
    - Files that git ignores, such as `.env`, are not copied into a new session. List them, and a setup script to run, under Side sessions in the workspace's settings.
18. To see what takes the server computer's memory and processor, expand Resources in the workspace's settings (the workspace's sessions, with their heaviest processes) or in the AI environment (every workspace that works or still has processes running, the server itself and other processes). Both show the computer's memory and warn when little is left. In the drawer, a working workspace shows its memory and CPU under its folder. CPU is a share of the whole computer. A workspace marked "Not working" there still has processes running that its work left behind. This only shows what is taken; stop the workspace's work, or end processes on the server's computer, to free it. It needs a server on Linux.
19. While the AI works in a git repository, a When Done button above the message box shows Commit or Keep Changes for the current work, loop runs included; press it to change it. It starts at Keep Changes for a sent message, so a question or an unfinished reply is not committed. A commit uses a message the AI writes, takes everything uncommitted and pushes when there is an `origin`. Nothing is committed for work that is stopped, fails, or that the AI says it cannot finish. While it commits, nothing else starts, though you can still queue input or start a loop.

20. Queuing what is typed or attached (Next in Send Options, or Alt+Enter in the desktop and web clients) sends it once the current work is done (at once when there is none) and commits after it unless Keep Changes was chosen (Alt+Enter keeps the commit setting of a loaded draft). When work is under way and the queued input is to be committed, the current work is committed first, so each gets a commit of its own (not when you turned its commit off, or it is a queued step you keep uncommitted to group it with the next). Queued inputs run one at a time in order, even with every client closed, and go ahead of a loop's runs. At most 200 can be queued.

21. The AI is trusted to work unattended: queued inputs, loops, tasks of new sessions and bring-ins tell it nobody may be there, so it decides for itself, notes what it assumed, and says when it cannot finish. Nothing waits for your approval and work that goes wrong holds nothing else up: while the AI cannot run (an outage, a usage limit, being signed out) its input is kept and tried again after growing waits; other failures are tried three times; work it cannot finish is skipped and not committed; and the AI is told next time what was left unfinished. Only Stop holds things back: when a chat has anything that runs by itself, stopping its work holds its queue, loop and bring-ins until you press Resume (sending and queuing never resume it). After a restart, queued inputs and loops go on, and work that was under way is taken up again, with the AI checking what it already did (it is given up after three restarts during it).

22. The status line above the conversation says what the chat waits for, with Resume, Stop Retrying (gives up on work that waits to be tried again), Cancel Auto Resume or Cancel Waiting Work when they apply. Pressing it, or the Up Next button beside the message box, opens Up Next: everything that will run by itself, in order, with why it waits; queued inputs can be edited, have their commit turned on or off, be run in a new session or be deleted, and bring-ins have a commit switch. The Activity tab lists each piece of work with how it went, the AI's final report, its commit and push, what was brought in and what happened along the way; entries that need attention are marked, and a notification says "<workspace> needs attention". It keeps the newest 500 per chat and is not a backup.

## Use the web client

`Client/Web/index.html` is a single static file with the same screens and behavior as the client apps: serve it from any static host such as GitHub Pages (or open it from disk) and enter the server's host, port and access key. It always connects with `wss`. The settings are saved in the browser. With a self-signed server certificate, open `https://host:port` in a tab once and accept the certificate; the connect screen links there. In a desktop browser Enter adds a line, Shift+Enter sends a message and Alt+Enter queues it.

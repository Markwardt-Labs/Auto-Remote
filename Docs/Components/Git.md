# Git

Git support lets a client show and drive the git repository of a workspace without ever running git itself. Everything here runs in the server's `GitService`, reached through remote commands.

## What is a repository

A workspace is a repository only when its folder is the root of one (`git rev-parse` reports an empty prefix inside the work tree). A workspace inside a larger repository, or a folder with no repository, reports `isRepo` false, and so does a server without git installed. `GitSetRemote` is the one way to make a plain folder a repository: it runs `git init` and adds `origin`.

## Reading state

The status comes from a handful of cheap commands: the branch from `symbolic-ref`, the head commit's subject and abbreviated hash from `log -1`, a tag from `describe --exact-match`, pending changes from `status --porcelain` and the remote from `remote get-url origin`. Changes come from one `status --porcelain=v1 -z --ignored=matching --untracked-files=all`: every untracked file is listed on its own, an ignored folder is one entry ending in `/`, and a rename is reported by its new path as modified. Clients derive the color of a file or folder from that list: its own entry first, then an ignored ancestor, and for a folder what lies under it (all new is new, anything else is modified). Read commands set `GIT_OPTIONAL_LOCKS=0` so they never fight the index lock of an AI that is running git itself.

History is `git log` over every branch, tag and remote branch plus the head, in date order, paged with `--skip` and one extra commit read to learn whether more exist. Branches and tags come from the `%D` decorations; a decoration naming a remote-tracking branch is told apart from a local branch containing a slash by checking it against `for-each-ref refs/remotes`. Each commit also carries its parents (`%P`), which is all a client needs to draw the branch graph: it walks the commits newest first keeping one lane per open branch line, so a commit takes the lane of the child that expects it, its first parent stays in that lane, further parents of a merge open or join other lanes, and lines that are not needed any more end where branches meet. The layout is done on the client because it only depends on the commits it already loaded, so older chunks just extend it. A commit's changed files are diffed against its first parent, or listed as all added for a root commit.

## Diffs

Clients get the whole file with its changes marked rather than hunks, so the server asks git for a unified diff with a million lines of context and parses it into one sequence: unchanged, added and removed lines, each with the line number before and after. This reuses git's own diff algorithm, so neither the server nor the clients carry one. The working tree is diffed against `HEAD`; a new untracked file, which `diff HEAD` does not list, is diffed against `/dev/null` instead. Binary files come back flagged with no lines, and a diff stops at 5000 lines.

## Acting

Commit stages everything (`add -A`), refuses when nothing is staged, commits and then pushes the branch to `origin` when one is set; the push is best effort so a failing remote never turns a made commit into an error. Reset is `reset --hard` plus `clean -fd`. Branch is `checkout -b`, tag is an annotated tag at the head. Failures return git's own message, for example the missing identity ("Please tell me who you are"), since the server runs as a user who is expected to have git set up.

Auto Commit is two calls from the client: `GenerateCommitMessage`, then the ordinary `GitCommit` with the answer. In a workspace on a local model both calls to the AI wait their turn for it: the question below, and the resolving of conflicts further down (cancelling either while it waits fails the request, or undoes the git action). The question goes to the workspace's AI as a fork request, so it runs in a throwaway copy of the conversation, which stays as it was and does not count as the AI working. The first line of the answer is used, stripped of quotes and a trailing full stop. The AI is told to describe only what the diff itself shows and to ignore the conversation it forks from, so a message does not name the tasks or requests that led to the changes. It is asked for about six words. A message is never cut off to fit: an answer of eight words or less is used, and one of nine or more makes the server ask once more, with the too long answer and its word count. The second answer, if it is not empty, replaces the first and is used whole (the first stays when the second is empty), and the call fails with an error when the message it ends with has twelve words or more.

Every action that changes the repository is refused unless the workspace is ready, so it cannot race the AI's edits.

The server also makes this commit by itself after the AI's work when its commit is on, taking the workspace straight on from the work, and then checks whether it was pushed, since a push that fails does not fail the commit.

Auto Commit has no dialog of its own to show an error in, so when any step fails (a refusal, nothing to commit, the AI failing or answering with twelve words or more) every client shows the reason in an "Auto Commit" notice; the notice is allowed even while git or AI work locks the other prompts.

## Workflows

Everything beyond a single command runs through `WorkspaceVersioning`, a port of Auto Dev's versioning service. `Perform` is the gate: one action per workspace at a time (a second is refused), and only while the workspace is Ready (a git action puts it in the Managing state), a `GitChanged` event when it starts and ends, and a snapshot taken first (checked out branch, head, whether changes were pending, every local branch tip, any operation already paused). When the action is cancelled (`GitCancel`, `StopWorkspace`, `CancelWorkspace`, or the server shutting down; a client disconnecting does not cancel it, since mobile clients drop and reconnect) or fails unexpectedly, it is undone: a rebase or merge it left paused is aborted, what was checked out is checked out again, and the branches it had actually written by then are put back (for a single command such as a commit, the checked out one). What it already pushed stays, and the message says so. A refusal with a message (`RequestException`) is a normal answer and restores nothing by itself; the workflows clean up after their own failures.

## Never losing work

The guiding rule is that nothing the action did not make itself may be lost, since it may be the user's: ignored files, files a script or an editor wrote while a long conflict resolution ran, paused operations, and commits made on other branches or pushed by someone else. `GitSafeguards` holds the checks.

- Squash, Rebase, Merge and Checkout are refused while a rebase, merge, cherry-pick or revert is paused (Sync skips), because cleaning up after a failure would abort it; an undo never aborts one that was paused before the action.
- Before a branch is moved or deleted its old commit is kept under `refs/auto-remote/backup/` (the newest 100), so a missed case still loses no commit; these references show in no history or branch list.
- Commands that change the files are never killed by a cancellation (that would leave the index locked and the tree half switched); the cancellation is acted on between them.
- Undo uses no hard reset and no `clean`. A head moves with `reset --keep`, or `reset --mixed` (files untouched) when changes were pending or a file git does not track is in the way, and a detached head is detached from the branch a rebase left checked out before it moves. Before aborting, whatever differs in tracked and staged files from how git left them at the conflict (a resolution, other edits, newly staged files) is stored as a stash entry (untracked files stay where they are, and leaving them out lets the entry apply), and a commit made meanwhile that no branch reaches is kept with the backups. If the changes cannot be stored, the abort would write over a file git does not track, or git refuses it, the rebase is left paused where it is, with nothing else checked out, and the message says so.
- No step overwrites a file git does not track, ignored ones included (git does so silently by default): checkouts and fast-forwards use `--no-overwrite-ignore`, and a rebase is refused (also before it continues after a conflict) when anything the target holds or a replayed commit touches would replace such a file, also where a file and a folder would change places. Rebases ignore the user's `rebase.updateRefs` and `rebase.autoStash`.
- Full reference names are used throughout, since a tag may share a branch's name.

Checkout accepts a local branch, a branch that exists only on the remote (a tracking branch is created), a tag or a commit hash (the last two detach). Pending changes are discarded only when asked to, and only once the checkout worked: they are set aside in a stash meanwhile, so a refused checkout discards nothing (if they cannot be restored as they were, the stash is kept and the message says so). Discarding is refused when writing the committed files back would replace a file git does not track. Files with unresolved conflicts cannot be stashed, so they are stored in a stash entry as they are, which stays, and the tracked files are reset first; what would stop the checkout is looked for before that, and if it is refused all the same, the message points to the stash. Delete removes the branch or tag locally and on the remote when it exists there.

Squash builds one commit from the branch tip's tree on top of the merge base with `commit-tree` and moves the branch with `update-ref`, so it works on any branch and never touches the working tree; it then force-pushes. Rebase squashes first when asked, skips the replay when the branch is already built on the target, checks the branch out (git can only rebase in the working tree), rebases, force-pushes and returns to what was checked out, a detached head included. Merge rebases the source onto the target when needed, fast-forwards the target (checking it out), pushes it and deletes the source everywhere, which is why the target is left checked out; from a detached head holding commits no branch has, it is refused. Both need a clean working tree.

Rewriting never erases someone else's work. Squash, Rebase and Merge first fetch the branch and refuse when the remote has commits the local branch does not contain, with two exceptions: the local branch holds the same change as each of them (`git cherry`, confirmed by comparing the patches exactly since git ignores white space there, and none is a merge), as after rebasing pushed commits or amending only their messages; or the remote's commit is the one the server replaced with a rewrite whose push has not gone through yet, and the branch still contains that rewrite (both are noted under `refs/auto-remote/unpushed/`), so the push can be repeated. Neither that the local branch once pointed at a commit nor that it was pushed from here is enough, since commits dropped by a reset or a revert would pass. After amending the content of pushed commits, the force push is therefore the user's to make. What a rewrite replaces on the remote is kept with the backups, and the branch is pushed with `--force-with-lease` against the commit that was looked at; Merge deletes the remote source branch the same way, so a push made meanwhile makes the step fail instead of being lost.

Conflicts are resolved by the workspace's AI: the server prompts it with the conflicted files and waits until it is idle again (polling, with no time limit, since a local model can take hours; stopping the git action ends the wait), up to three attempts, then continues the rebase (or accepts that the AI finished it). An AI without the shell (the default of a new workspace) can edit files but not stage them, so after each attempt the server stages what the AI visibly settled: a file whose conflict markers are all gone, or one it deleted. A conflict with nothing to edit whose file is still there, such as a binary file, or one a side deleted that the AI wants to keep, says nothing about what was decided, so only an AI with the shell can settle it. When the AI cannot be started, does nothing, or the attempts run out, the rebase is aborted and the action fails with a message; the conversation shows what the AI was asked and did. A resolution that takes the target's side whole empties a commit, which git drops without a word, so before continuing, a stopped commit with nothing left of it takes the rebase back. When the AI moved the rebase along itself, it is taken back if it ends with fewer commits than the target was missing.

The automatic fetch and pull are `GitSync`, driven by the clients (when a workspace gets the focus, every minute while it is focused, and when the history opens). It fetches with pruning; local branches checked out in no work tree are moved to match the remote only when they have nothing of their own (unchanged since they were in step, checked again after the fetch, or an ancestor of the remote; a move that is not a fast-forward keeps a backup); and when the checked out branch followed `origin`, its counterpart there was deleted (for example by someone else's merge cleanup) and the remote had everything the branch holds, the head is detached at the same commit and the branch deleted. It then fast-forwards the checked out branch when the remote is ahead, stashing and restoring pending changes around the pull and having the AI resolve conflicts of the restore. It does not pull when stashing would lose something: an ignored file where a file and a folder changed places, or edits to files marked assume-unchanged or skip-worktree. It restores exactly the stash it made (git makes none when only a submodule changed), with what was staged. The stash is dropped only when everything came back as it was; otherwise it is kept, also after the AI resolved conflicts, since a resolution can make conflicts go away by discarding. Clients say nothing about a sync that fails, so whenever a stash is left behind the server also reports it as a failure of the workspace, which shows in the conversation and the error history. Sync is a background action: it is not reported as busy and sends `GitChanged` only when it changed refs, the head or the working tree, and it does nothing while the AI is working, another action runs or a git operation is paused. Only while it changes what is checked out (the fetch can take long, so everything is checked again after it) is the workspace in the Managing state, which keeps new AI work from starting under it and lets `StopWorkspace` end it.

Side sessions are worktrees on branches under `auto-remote/session/`. Git actions refuse those branches in every workspace, history shows each as a `Session` ref under the session's name (and leaves out any the server no longer knows), a commit on one is never pushed, and a side session's own git is limited to history, changes, commit and discard. Their changes since the session started, and the diff given to an integration, compare two trees: the one recorded when the session was made and one of the files as they are, built in a copy of the index so that new files count and the real index stays as it is.

Squash, rebase and merge need a git identity (git commits on the user's behalf); the status says whether git knows one, and clients ask for a name and email first (`GitSetIdentity`, written to the server user's global configuration).

## Cloning

`CloneWorkspace` creates the clone's folder inside an existing folder, named by the request or after the repository, and refuses an existing folder. The clone is made in a temporary folder inside the parent and renamed once it succeeded, so a clone that fails, runs out of time or is cancelled leaves nothing and never removes what something else made under the name. It runs for as long as the clone takes (up to 30 minutes), unlike every other git command, which is cut off after two minutes.

## Safety

Git always runs with an argument list and no shell. Anything a client controls that could be read as an option is validated: URLs may not start with `-`, commit arguments must be hexadecimal hashes, the names of new branches and tags go through `check-ref-format` (an existing one must name a ref that exists, and may not start with `-` or hold spaces or control characters), and paths may not be absolute or contain `..`; the clone URL is also passed after `--`. Git never prompts (`GIT_TERMINAL_PROMPT=0`, ssh in batch mode unless `GIT_SSH_COMMAND` is set), so a missing credential fails fast with a message instead of hanging, and only the file, https, http, git and ssh transports are allowed.

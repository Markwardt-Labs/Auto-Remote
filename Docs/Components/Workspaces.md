# Workspaces

A workspace is a folder on the server's machine that the user works in. An AI session is a conversation with the workspace's AI service (Claude Code, OpenAI Codex or local models through OpenCode) that the server creates and attaches to a workspace the first time it is prompted. The two are separate: the workspace is the durable thing the user sees and manages, the AI session is replaceable.

## A workspace is its folder

For each workspace the server stores its identifier, the AI session attached to it, the group it is filed in (if any) and the few choices that are Auto Remote's own: its review and expand prompts, its status interval, whether its chat shows the AI's work, whether its AI may delegate and what new side sessions get. A side session is also stored as a workspace, a hidden one with a record of its own that gives its folder, provider and name; what follows about folders and names is about every other workspace. The folder, the provider and the other AI settings are the session's: the workspace's folder is the path the session works in, read from the session when the server starts, and its display name is always the folder's name. Renaming a workspace therefore renames the folder on disk, and the server refuses when another workspace lives inside that folder or the target name exists. Creating a workspace requires an existing folder (the client can create one while browsing, starting from the config's `defaultFolder`), and one folder hosts at most one workspace; the session is made together with the workspace, so a workspace whose session cannot be made (an API key for the local provider, or local models without a model for every capability) is not created at all. Renaming a workspace renames its folder and then tells the AI session; when that fails the folder is renamed back. Moving a workspace to another folder (`MoveWorkspaceToFolder`) is only telling the session: Live AI tracks where a workspace is, and moves the tool's conversation along where the tool keeps it by folder, without loading the session, so it works even when the old folder is gone (the project was moved on disk). The server never moves files for it. A workspace can also be cloned: the server runs `git clone` into a new folder inside an existing one and creates the workspace there.

## Deleting

Deleting removes the workspace with its attachments and chat and ends its live AI session. It first cancels the integrations into it and permanently deletes its side sessions and their branches, also when the folder is kept; when the folder is deleted too, the AI service's stored conversation goes with it, otherwise it stays in the service's own storage. Deleting the folder as well is the default and recursive, so the server refuses it for a file system root, the server user's home folder or any ancestor of it, and any folder that contains or sits inside another workspace (the workspace's own side sessions do not count). Rename and delete are refused unless the workspace is ready. Deleting also removes the workspace's work that waits for the local AI, its loop and its activity, and ends the tasks it delegated.

## AI sessions and the live conversation

The AI backend is Live AI (the `Markwardt.LiveAi` library), which drives the `claude`, `codex` or `opencode` command line tool (OpenCode for local models). The server keeps one live session per workspace, opened the first time the workspace is prompted and shared by every client. The tool runs with the workspace folder as its working directory, so the project's own instruction files apply as they do in a terminal (`CLAUDE.md` for Claude Code, `AGENTS.md` for Codex), and its process stays alive between prompts. The tool's own file and shell tools are switched off; the AI works through Live AI's tools instead: file tools over the whole machine, with the workspace folder as the current directory (where the settings allow files outside the workspace, absolute paths work), and a shell that starts in the workspace folder. A shell command runs to completion, for 120 seconds unless the AI asks for longer (at most an hour), and ends with the prompt. Nothing is ever asked permission for.

That is also what keeps the AI from leaving work behind: without the tool's subagent, background and scheduling tools it does everything itself, and a workspace goes back to Ready when the AI has answered every prompt it was given. The server builds instructions into every session that keep that true while still letting the AI report on time: the AI keeps its turn open until all of the work is finished and replies only then, with the final summary. For long work it is told to start it in the background, with the background option of the shell and delegate tools (helpers can run in parallel), and to follow it with Live AI's task tools: it calls the wait tool with a timeout equal to the status interval, which returns when a task ends or when the update is due, writes a short status update as a normal message (what it has done and what comes next), and waits again, so the chat stays alive while the long work runs. It must wait for every task and helper to end before it replies, and leave nothing running afterwards; scheduled or recurring work stays forbidden. Background commands need the shell to be allowed in the workspace, helpers do not. This keeps the chat from going quiet during a long run since every message of the AI shows in the chat tab. The interval is a global setting (default 5 minutes) that a workspace can override, and it is part of the instructions, so a change of either rewrites them: in the open sessions at once, in the others when they are opened. The instructions are stored in the session's instructions in front of the user's own, wrapped in a marker the server recognizes so that an older wording or another interval is replaced, not doubled, and which the server puts there whenever it creates, opens or changes a session (so older workspaces get them too), and takes off again when it reads the settings, so the user never sees them and cannot remove them.

The session is identified by Live AI's identifier (32 hexadecimal digits), stored as the workspace's `sessionId`; Live AI keeps the link from it to the tool's own session in a `liveai` folder in the data folder, and the tool keeps the conversation in its own storage, so it stays usable from the tool itself. Sessions an older server stored with Live AI 1.x are upgraded when the server starts and continue with their history: the link that names the tool's session is rewritten for Live AI 2.0 and the tool's conversation is untouched. A workspace that holds the tool's own session identifier written with hyphens, from before Live AI was used, cannot be continued: it is given a new session with an empty conversation when the server starts, and the old conversation stays in the tool's own storage. When a session can no longer be loaded, a new one replaces it, keeping the workspace and its folder and provider, with an empty conversation. A workspace whose session link is gone altogether stays in the workspaces file but is not listed, since its folder is unknown; it comes back if the link does (a side session records its folder, so it stays listed). When the loaded session's folder is not the workspace's, the session is moved to it.

A prompt is published as a `MessageAdded` event as soon as the server accepts it, and each message the AI writes as it writes it. Accepting can take seconds (the usage check, a snapshot of the files, opening the AI session), so the client that sends a prompt shows it at once as its own pending message (marked Sending…, never sent over the wire) and swaps in the server's copy, the `MessageAdded` whose text matches, in place; the events and the response arrive in either order, so a successful response alone removes nothing. Pending messages stay at the end, after whatever arrives meanwhile, are never counted or trimmed as part of the stored chat, survive the chat being read again unless what was read holds their copy, and are removed when the server refuses the prompt (the text goes back into the box) or queues it, where the queue banner shows it. Files not uploaded yet show by name. A prompt sent while the AI works is steered into the work at once with Live AI's standard send, which is how the user can always add to what the AI is doing, and it is never sent a second time as long as the AI acted on it. The tools sometimes swallow such a message (Claude Code takes it in and ends the turn without answering it), so the server remembers it and, when the AI's turn ends, reads the stored conversation back from the end to the start of that turn: a message the AI wrote or did something after is done with, while one that has nothing after it, or that the conversation does not show at all, is sent again as a turn of its own with a note that it may have been missed, and that second copy is not added to the chat. A prompt that arrives as a turn ends (the session is not yet or no longer working) is queued and sent right after, in the order sent. The workspace stays Working across all of these hand-overs and only returns to Ready once nothing is steered or queued any more, so a prompt sent just as the work ends is never lost. Stop forgets what is steered or queued, and so does a failure of the AI. If the AI fails (not signed in, out of quota, the tool cannot start) the work ends and the failure is reported as a `Failed` event; the next prompt starts again. Images attached to a prompt are shown to the AI directly; other files it reads by their path.

An idle session is closed after five minutes, and also before a rename or a delete, so those apply from the next prompt; closing ends the tool's process and loses nothing, since the conversation is stored by the tool. When the server itself stops (SIGTERM or Ctrl+C) it ends the AI's work the same way and waits a few seconds for the commands to end before it exits, so none outlive it.

## Provider and settings

Each workspace has a provider, chosen when the workspace is created and never changed afterwards, because a session only exists in the provider that created it. The providers are Claude Code, OpenAI Codex and local models (OpenCode, which runs the models of a server on the server's machine such as Ollama, LM Studio, llama.cpp or vLLM); Live AI drives all three the same way, with the same file tools and shell. A new workspace takes the default provider of the AI environment unless the user picks another, and can be given an API key for just its session (Claude Code and Codex), which Live AI stores with the session and the server never keeps.

There is no list of models in the app: a session is configured with a capability (Fast, Balanced, Strong or Max) and an effort (Low, Medium, High or Max), and Live AI picks the model of the provider for them. Besides those the settings hold whether the AI is sandboxed, may use the web and may generate images, and standing instructions; a new session starts balanced and high, not sandboxed, with the web on and image generation off (image generation only works while the environment has an image service), and no instructions of the user's own. A sandboxed AI has no shell and its file tools reach only the workspace and what the server shares with it, such as attachments and work to bring in. It limits the AI's tools and is not an operating system sandbox, and turning the web off does not keep an AI that has a shell from using the network. The server keeps the sandbox with the workspace (off unless set, also for workspaces an older server stored) and puts it on the AI session whenever it opens it. Those are the defaults of the AI environment (the `New workspaces` part of it, which is edited with the rest of the environment and applies to every workspace created afterwards, not to existing ones), which the server gives the prompter's environment and Live AI applies to every session it creates, so the server needs no more than the workspace and the provider to make one; a workspace stored by an older release is not given them but what it ran with before (the shell, the web and files outside the workspace on, image generation when there is an image service, and the built-in instructions), once, so that it keeps working as it did. Edits in the settings panel are pending and go to the session together when the panel is closed. Live AI stores all of it with the session, so the settings are read from the session (`GetWorkspaceSettings`), also when a client opens them again, so a change made from another client shows, and written to it (`SetWorkspaceSettings`), applying from the session's next prompt, including to a conversation that is resumed. Of these the server keeps only its own choices named above; an idle session it closes after a change is simply loaded again. The session also describes how it runs (the model it chose and the settings it runs it with), which the settings show as read only lines.

Changing a workspace's settings gives them to the session for its next prompt, and Live AI writes them to the session's stored record as soon as they are set, so a change survives a restart or a crash without a prompt in between. A client sends the settings when the settings panel is closed (or the user switches workspace), and the AI environment likewise when its panel is closed, the server writing its file before it answers. When the server stops it also waits, for a few seconds, for every session to finish closing, which is when a session records the rest of its state. A client sends the settings only after it has read them from the server once, and puts an edit it made before that on top of what the server said, never on top of default values, because the server applies a whole settings object as it is, and one made of defaults would turn off the shell, the web and image generation of the workspace. The server logs every change that actually changes something, with the connection that sent it and the values before and after, so an unexpected change can be traced to its sender (the connection's port names the client process in `ss -tnp`).

The AI environment is the one place for what is the same for every workspace: it is applied to the single prompter that all sessions are made on, and the server keeps it in its data folder. The local provider needs a model for every capability there, and a session that cannot be made for lack of it fails with that message.

## States

A workspace is always in exactly one state: Ready (nothing runs), Working (the AI is running), Managing (a git action is running), Stopping or Canceling (the work is being ended, below). The server owns the state in one place, a tracker that the prompt service and the git workflows each enter when their work starts and leave when it ends, so the check and the change are one step and two requests racing for an idle workspace cannot both win. Work only starts from Ready: a workspace in any other state refuses the others (a prompt during a git action, a git action while the AI works, and rename and delete in every state but Ready) with a message naming what is in progress, and the work that holds the workspace has to end first. The one exception is AI input: a prompt is accepted in Ready and Working, where it joins the work in progress, and refused in Managing (attachments can be uploaded in any state). Scripts are not a state and not work in this sense: they run beside whatever the workspace is doing and never refuse or are refused for it.

A git action can use the AI itself to resolve conflicts. That AI work is part of Managing rather than a change of state, so the workspace stays Managing until the action ends, and if the AI is somehow still busy then, the workspace falls to Working instead of Ready. The automatic fetch and pull is not a state: it runs only from Ready, is not reported as busy and does not stop other work from starting. A fetch the user asks for is a git action like any other.

Work in Working or Managing can be ended by hand. Stop ends it at once and keeps what it did: the workspace is Stopping meanwhile and Ready afterwards. Cancel, only for the AI's work (Working), ends it and puts back what it did: Canceling meanwhile, Ready once reverted. Git actions can only be stopped. Stopping and Canceling are not Ready, so nothing else starts, and they cannot themselves be stopped or cancelled; every other state refuses a second stop or cancel. Stopping the AI interrupts it (the work it did stays in the conversation, which the AI is told, and the next prompt carries on from there); a shell command the AI was running does not end by itself, since it runs in the server, so when one is still running the session is closed as well, which ends the command and the tool's process, and the next prompt opens the session again and resumes the conversation, and a git action cannot be left half done, so stopping it undoes it (the AI that was resolving its conflicts is interrupted too).

Reverting the work of the AI needs a git repository: when the work starts from Ready, the server records a snapshot, the head, the branch, the index and a tree object holding every file git does not ignore, untracked ones included, built in a temporary copy of the index so the real index and files are untouched. Reverting compares that tree with the files as they are, deletes the files and the emptied folders that were added, restores the ones that changed or went missing, then moves the head and branch back (when the work committed or switched branches) and puts the index back. Ignored files, branches the work created, repositories it made inside the workspace and anything it pushed are not reverted; what was ignored when the work started stays even if the work changed what git ignores (a folder counts as ignored only when git ignores the folder itself, not merely everything that was in it), and where such files are in the way of a file to restore (a file and a folder changed places) that file is left and the revert says so. The snapshot is dropped when the work ends normally, and a workspace that is not a repository has none, so reverting is refused there (Stop is not). No client offers it: the clients only stop work, and cancel only a loop.

Clients show the state: the header is blue in every state but Ready (running scripts do not turn it blue; the Script tab and the file system show them), the message box is locked in every state but Ready and Working (and says why), buttons that start work are disabled or refuse with a message, and the Managing state offers Cancel and undo for the git action. They work it out from the events and statuses they already receive (the AI working, a git action busy) and take Stopping and Canceling from the `StateChanged` event, which wins, while the server remains the authority. While the workspace is Working, Managing or Canceling the empty message box shows the work buttons: Stop in every one of those states (disabled while Canceling, which cannot be stopped). Stop is confirmed with an "are you sure" question that closes by itself if the work ends meanwhile. The send button shows whenever something is typed or attached. In Working it sends into the work, since more AI input is still accepted then; where the chat takes nothing at once it opens Send Options, beside Stop, so the input can be queued or given to a new session.

## Loops

A loop sends one prompt to the AI over and over, for as long as its condition allows. It is set up with a prompt (the review prompt or the expand prompt in use for the workspace, or the user's own), the minutes from the start of one run to the start of the next (zero runs again as soon as a run is done) and a condition that ends it by itself: never, at a time of day (the next time it is), after a length of time (up to 24 days), after a number of runs, or when a usage window of the service reaches a share of its limit (offered only for services that report windows, and read from the service's usage before each run and once a minute while one runs). The server runs loops itself rather than through Live AI's loop: a run is an ordinary prompt, sent once the workspace is Ready and the AI idle, so a run never overlaps a git action or a prompt of the user, enters Working and captures the snapshot like any other work, and is shown to clients as the user's message with the AI's replies after it. In a workspace on a local model a run goes through the local AI work queue like any prompt, so it can also wait for the work of other workspaces, and the interval then counts from when the run starts. A loop also waits while a bring-in is about to be given to the AI, while a commit that follows work is under way or due, while work is to be tried again or a queued input is to be sent, while the chat is stopped and while delegated results are outstanding. Each run is committed when the loop is set to. A run is only given when the AI is idle, never steered into or queued behind work it did not start, and not again before the interval since the start of the last run has passed and its work is done, whichever is later (so a prompt of the user or a git action in between delays the next run rather than sharing it). A prompt the user sends while a run works is steered into it and followed up like any prompt, before the next run starts. A loop can be started while the AI is working or its changes are being committed, and its first run then waits until that is done. The loop says whether a run is under way (`isRunning`), told before the run's prompt is sent. A workspace has at most one loop, which is kept in `loops.json` and goes on after a restart, and while it runs the server keeps the AI session open (the idle close and the service switch wait for it).

A loop ends when its condition is met or when it is cancelled. A run that fails or that the AI says it cannot finish never ends it. A run the AI could not make (see unattended work) is not counted and is made again after a growing wait, which clients see as `limitCheckAt` of the loop, as is one that cannot be sent. Ending a loop never cuts off work: whether its condition is met or it is cancelled, the run in progress finishes and the loop only stops sending prompts. Stop and Cancel do not end it: the chat is stopped, which holds the loop until the user resumes it. Renaming or deleting the workspace cancels it first. Clients learn of every start, run and end as a `LoopChanged` event, with the reason when the loop ended by itself, and read the loop with `GetLoop` when they open and reconnect.

## Pausing at the usage limit

The global settings hold a maximum for the usage windows of each AI provider that reports them (`claudeMaxWindowPercent` and `codexMaxWindowPercent`, 95 by default), set in the section of the provider; there is no single maximum, and the local models, which report no usage windows, have none and are never held back. While the AI works in a workspace the server reads the usage windows of that workspace's provider every 30 seconds (the reading is the one the prompts keep up to date, so it costs a prompt of its own only when none reported the windows lately). When a window is at or past the maximum of that provider, the server sends the AI the same "pause current work" a user's pause button sends, which joins the work in progress, and holds the workspace in an automatic pause: the pause is part of the history, and every client is told of it with `LimitPauseChanged` events and shows it in the chat and in the header. Every 15 minutes the server reads the windows again, from the provider and not from what was read before, and tells the pause again when a window is still at or past the maximum (the event then carries the newer reading and the time of the next check). Once no window is at or past the maximum it waits for the AI to be idle, since the pause is carried out as a message the AI reads between steps, then sends "resume unfinished work" and ends the pause. A reading that cannot be taken counts as still past the maximum, and a resume the workspace refuses (git is running there) is tried again in 30 seconds.

A loop obeys the same maximum. Before each prompt it asks the guard: when a window is at or past the maximum the loop sends nothing, and the workspace is held in the same automatic pause, except that the AI is idle and nothing is sent to it; that pause ends by itself, without a resume prompt, once no window is at or past the maximum, and the loop goes on with its next run. A loop whose run was paused with the AI continues the same way after the resume. While the workspace is paused its loop sends nothing either way.

A person can step in in two ways. `CancelLimitPause` ends the pause without resuming the AI, turns the commit off and stops the chat when it has anything that runs by itself, so nothing goes on until the user resumes it (the AI is not paused again while it finishes what it was doing). And a prompt of a user is refused, with the window in the response, while a window is at or past the maximum or the workspace is paused, unless the request says `ignoreLimit` after the user confirmed in a popup: then the pause ends without a resume and the workspace ignores the maximum until the work that prompt starts, or the work in progress, is done; the next work is held to the maximum again. The prompt that pauses the work is never refused. The pause also ends, with nothing resumed, when the work is stopped and when the workspace is deleted; a message of a user does not end it by itself, and neither do the messages of the pause and resume buttons or of the server.

## Groups

Workspaces can be filed into groups, which can contain other groups to any depth; the client shows the result as a tree. A group exists only in the server's workspaces file: it is organization for Auto Remote and has nothing to do with the folder hierarchy on disk, so filing a workspace never moves anything and the workspace folders keep their real parents. A workspace is in at most one group and a group has at most one parent. Names are unique ignoring case among the groups with the same parent. A group cannot be moved into itself or into anything inside it. Deleting a group keeps what is in it and moves its workspaces and groups up into its parent (to the top level if it had none). Groups have a custom order that every client shows: new ones go to the end, renaming keeps the place, moving into another group puts the group at the end of it, and the order is changed one place at a time with the shift command, which only swaps among sibling groups (those of one parent) and stops at the ends. Workspaces have no manual order: within a group (or at the top level) clients list them by when their AI session was last loaded, the latest first, except that the working ones (in any state but Ready, in any of their sessions) come first, highlighted in the blue of the working header (as is every group around one, which does not move), and after them the ones a loop runs in, which show a loop icon (the client follows `StateChanged` and `LoopChanged` events for this, and the list names the busy and looping workspaces when it is read; a state heard while the list was on its way wins over it, since states change often), and the server reads that timestamp from Live AI whenever the workspaces are listed and announces a change when a prompt is sent so the order follows the work. Sub-groups are listed before the workspaces, and groups start collapsed, except that focusing a workspace opens the groups around it. A new workspace can be filed into a group when it is created or cloned. Groups are managed from the workspace listing, not from a workspace's settings, and live server side so every client sees the same organization: the server announces each change with a `WorkspacesChanged` event and clients list the workspaces again, so a workspace created, moved or deleted from one client shows up in the others at once.

## Attachments

Files attached to a prompt are kept in an `attachments` folder in the data folder, one subfolder per workspace, under a name prefixed with a random id, and are deleted with the workspace. A prompt names them by path (images are also sent along with it). That folder is outside the workspace, so every AI session of a workspace is granted read access to its own attachments, never write access, also in work that is already running; reading them takes no access to other files outside the workspace.

## The AI's work in the chat

Besides what it says, the AI calls tools, and the chat can show those calls and their results: dimmed, smaller text that is not formatted, between the messages they happened between. A call is one short line made by the server from the tool and its arguments ("Read src/Program.cs", "Run dotnet build", "Write notes.md (12 lines)": the tools of the library have a wording of their own and any other tool is its name with up to three short arguments), and a result is a count or one short line ("→ 120 lines", "→ 3 matches", "→ Failed: no such file", "→ No output") that is never the content of a file or the output of a command, so a work entry is a description of work and not a copy of what it handled. The server pairs a result with its call by the id of the call to know which wording applies. Whether it does is a choice of the workspace, kept by the server with the workspace (`showWork`), so every client sees the same chat; it starts as the choice for new workspaces in the global settings (off unless changed) and is toggled with the button beside the auto scroll button of the chat. The server records the work messages always, so turning the choice on shows the past work too, but it only hands them out when the choice is on: the history leaves them out otherwise and counts only the messages it hands out, so a chunk is never mostly hidden work. Live work messages are published to every client, and a client that does not show them drops them. Changing the choice sends `ShowWorkChanged`, and every client reads the chat again, which also tells it the new state. The work of a conversation made before this existed is not there; only the tool calls and results from the feature on are. Every tool call of the session counts, the AI's own tools and the ones of the library alike; what the engines do not report, such as the reasoning of a model, is not part of it.

## Streaming

While the workspace shows the AI's work, what the AI writes also appears as it is written. The engines report a message in pieces before the whole message, and the server passes the pieces on as `MessageDelta` events, gathered for about 100 milliseconds so that a client lays its text out ten times a second at most, not once for every word. A client puts the pieces together as a message of the AI at the end of the chat, grows it in place, and replaces it with the finished message when that arrives, wherever it has got to by then (the work between is not moved). Which workspaces stream is the server's decision, from the same choice as the work itself, so a workspace that does not show the work sends no pieces at all and costs a client nothing; the server follows a change of the choice at once, also in the middle of a message, through the `showWork` of the `ShowWorkChanged` event. The reasoning of a model that thinks before it answers (OpenCode and Codex report it, the only sign of life of a local model that reasons for minutes) is passed on the same way, as pieces that only appear while the workspace shows the work. What the tool does on its own that takes a while and writes nothing (summarizing the conversation when the context window is full, asking the model to go on after it ran out of output tokens) is a work message, shown like a tool call. The reasoning is the exception to the pieces not being stored: the server also collects it, and when it ends (the next thing the AI does, or the end of the work) publishes and stores it as one work message with the time it started (`isThought`, cut at 20,000 characters) in the place it happened, which a client shows in place of the pieces it streamed (a piece carries `thought` so the client builds the streamed text as a work message from the start); it is stored whether or not the workspace shows the work, so turning the work on later shows it. The other pieces are never stored: the chat file only holds finished messages, a piece that was not sent yet is dropped when its message is finished, and a message the AI never finished (it was stopped or failed) disappears from the chat when the work ends and is not there after the chat is read again.

## Error history

Work that ends without the AI writing a reply or calling a tool, which a local model does when it answers with nothing or runs out of output tokens while it reasons, would otherwise look like the AI stopping for no reason, so the server reports it as a failure ("The AI finished without writing a reply or using a tool..."); it does not when the work failed already or the user stopped it. A failure of the AI (it could not be started, a request failed, a limit was reached) is shown as the error line of the chat, in every client looking at the workspace, with the time it happened (the one the `Failed` event carries), and goes away from all of them when the next user message of the workspace arrives, whichever client sent it. The server therefore records every `Failed` event it publishes, by the workspace that event names, with the time it happened, and keeps the entries for 30 days: it listens to the event hub itself, so whatever publishes such an event is recorded without knowing about the history, and every client is told of the new history with an `ErrorsChanged` event. The settings of a workspace have an Errors section that lists its entries, newest first, with their times, read when the settings open, after a reconnect and whenever an event arrives. An error belongs to exactly one workspace: events and lists are addressed by workspace, the file is per workspace, and every workspace view of a client only follows the events addressed to its own workspace, so an error never appears in the chat, the error line or the Errors section of any other workspace. The history is for `Failed` events, which come from the AI and from side sessions (an integration that could not start, or files of a removed session that were left on disk, both reported on the main workspace); a failed git action or script shows where it happened and is not recorded.

## Drafts and queued inputs

A user can set the text of the chat input aside and bring it back later, from any client: saving adds an entry with the text and the time to the workspace's saved inputs and clears the input, and picking an entry from the list removes it and puts its text into the chat input (above what is typed there, should something be, so nothing is lost). The list is kept by the server, a `inputs/<id>.json` file per workspace in the data folder that is deleted with the workspace, so every client shows the same entries, queued inputs (which the server sends by itself, and which clients show in Up Next) first and then the others, the drafts, the last saved first, and a `SavedInputsChanged` event carrying the whole list keeps them current. Taking is done by the server, so two clients picking the same entry cannot both get it, and the one that lost reads the list again and shows that the entry is gone. A workspace keeps at most 200 entries, the oldest saved ones dropped first. Every entry has a delete button, which asks before it deletes. Voice input adds entries too: the client records on a full screen of its own with Complete and Cancel, and Complete sends the recording with `TranscribeSavedInput`, which adds an entry marked as being converted at once and opens the list on it. The server keeps that entry in memory only (it is not written to `inputs/<id>.json` until it has its text, since a half made entry would be stuck for ever after a restart) and merges it into every list it sends; the conversion runs in the background of the server, not tied to the request or the client that made it, so a client may leave or lose its connection meanwhile. When the text is ready the entry keeps its identity and time, gets its text and is stored, from then on indistinguishable from a saved one; when it fails it stays in memory with the reason. Deleting an entry, which also cancels a conversion or dismisses a failed one, is `DiscardSavedInput`, which removes it without handing it to anyone; an entry that is being converted or failed cannot be taken. Since all the entries of the list share one command in the clients, that command must not disable itself while it runs, or every entry would look disabled while the server answers for one. Saving is offered while text is typed and loading while the chat input is empty. The list opens over the whole chat panel, conversation and chat input together, so it has all the room there is, and closes when an entry is picked, from its Close button, or when text is typed.

## History

The clients show a window of the chat rather than all of it, since every message is a view to build and the work of the AI can make a conversation very long: the newest chunk on opening, a further chunk each time the user scrolls to the top of what is loaded, however many that makes, and back down to one chunk when the end is reached again or, while auto scroll is on, as messages arrive. With auto scroll on, two things alone move the chat to its end: new output (a message or a piece of one, also what a re-read finds beyond what was there), wherever the user is, and, while the user is at the end, anything that makes the chat taller, which keeps them there. Growth anywhere else is not new output (older messages loading, which can take several layouts, text wrapping anew, content drawn late), so the clients are told of output rather than inferring it from the height. A chunk is bounded by its text as well as by its message count: the server reads backward from the cursor while the messages stay within `characters` (20,000 by default) and `limit` (100 for the clients), always taking at least one message, and a client trims its window by the same two numbers, so the weight of a chunk does not depend on whether the conversation is a few long messages or many short tool lines, and the work messages of a workspace that shows its work count like any other. Each kind of message builds only its own view (a user's prompt, work, or formatted AI text), and a chunk is added or dropped with one change notification. The window's start is tracked as a position in the stored chat, which is what the history cursor is, so a client can load again exactly what it dropped. Loading an older chunk, or anything else that changes the height of what is above the message at the top of the screen (a text that reflows when the width changes, a message that is dropped at the top), never moves what the user is looking at: a client remembers the message at the top of the screen and where it is in the content, and after every layout scrolls by however far that message moved. Turning the work on or off, which changes the messages between the ones on screen, reads the chat again (the server tells every client with `ShowWorkChanged`) and never loads more than scrolling up would have: for a client that follows the end (auto scroll on and at the bottom) only the newest chunk is read, the work counting in its text like any other message, and for any other, whether auto scroll is off or the user scrolled up, the client reads backward until the oldest message it showed (the oldest that is not work, since that exists either way) is in the window again, but stops as soon as the window holds as much text as the one it replaces (at least one chunk, since the work between the messages can make the same stretch many times longer). When it stopped before that message, the place the user was at is too far away to bring back without loading what nobody asked for, so auto scroll turns on and the window is trimmed to the newest chunk. Otherwise it replaces the messages once and puts the messages that were on screen back at the same place, so the screen stays where it was. A reconnect reads the chat again the same way, and only output that is new to it moves a client with auto scroll on to the end, which also trims the window again. A message being streamed counts too: while auto scroll follows the end, its growth drops the oldest messages like a new one does. The Avalonia clients do it from the layout of the message list, which also keeps it right when several things happen while a chunk is being read (the user keeps scrolling, a message arrives), and the web client does the same with the browser's own scroll anchoring turned off, so every browser behaves alike; while auto scroll keeps a client at the end, growth scrolls to the end. The chat is kept by Auto Remote itself, one file per workspace in the `chats` folder of the data folder, and holds what the user sent and what the AI wrote, exactly as the events published them, plus the work the AI did on the way, its tool calls and their results, as work messages (`isWork`, always by the AI, cut at 2000 characters); interruption notes, the summaries a tool writes when it compacts a conversation and the host's own notes never get into it, and neither do the copies of a prompt the server sends again or the questions it asks the AI in a fork. A workspace that has no chat file yet (one made by an older server; never a side session, whose AI conversation starts as a copy of main's) takes over the stored conversation once, the first time its history is read, and leaves out the tool's compaction summaries, the host's notes and the repeated copies an older server sent again; from then on the file is the only source. The client reads the history in chunks, newest first. The chat is purged of its oldest messages beyond a limit, so a client cannot scroll back forever. A chunk comes with an opaque cursor for the messages before it, which the client sends when the user scrolls to the top, until a chunk has none. Events carry no position, so a client that opens a workspace subscribes first, holds the events that arrive while it reads the newest chunk, and drops from them the leading messages the chunk already ends with. A `history` folder in the data folder is not read and can be deleted.

## Files

Browsing a workspace's files is read only and confined to the workspace folder: paths are resolved and rejected if they leave it. Text files are returned up to 256 KiB, and files that look binary are refused. The AI may make a `.liveai-temp` folder in a workspace for data its commands produce and read (downloads, for one); Live AI marks it with a `.gitignore` so git ignores it, removes its files after a while, and removes the folder when the session ends, and being a dot folder it shows only with hidden files.

The view is live, also for changes made outside Auto Remote: a connection says which workspace its client is showing, and the server watches that workspace's whole folder, sub-folders included, for as long as some connection has it open (and gives up the watch when the last one leaves, or the workspace is renamed or deleted). Changes are collected until the folder has been quiet for 0.4 seconds, or for two seconds at most while it keeps changing, and then reported to every connection as one `FilesChanged` event per folder whose entries changed (more than 200 folders collapse into one event for the workspace folder marked `all`, meaning anything may have changed). Everything inside `.git` is ignored except the head, the index, the packed refs and the refs, which are reported as `GitChanged`, since a commit or checkout from a terminal moves them. A client refreshes the folders it shows and reads the git status again, and re-reads the open file when its folder changed, at most once every three seconds however often it changes, and only replaces what is shown when the content differs. If the operating system cannot watch the folder (the limit of watches is reached, for example), the server logs it and carries on without live updates for that workspace.

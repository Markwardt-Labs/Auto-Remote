# Workspaces

A workspace is a folder on the server's machine that the user works in. An AI session is a conversation with the workspace's AI service (Claude Code, OpenAI Codex or OpenCode) that the server creates and attaches to a workspace the first time it is prompted. The two are separate: the workspace is the durable thing the user sees and manages, the AI session is replaceable.

## A workspace is its folder

A workspace stores the folder path, its AI settings, the attached AI session and the group it is filed in (if any); its display name is always the folder's name. Renaming a workspace therefore renames the folder on disk, and the server refuses when another workspace lives inside that folder or the target name exists. Creating a workspace requires an existing folder (the client can create one while browsing, starting from the config's `defaultFolder`), and one folder hosts at most one workspace. A workspace can also be cloned: the server runs `git clone` into a new folder inside an existing one and creates the workspace there.

## Deleting

Deleting removes the workspace and its attachments and ends its live AI session; when the folder is deleted too, the AI service's stored conversation goes with it, otherwise it stays in the service's own storage. Deleting the folder as well is the default and recursive, so the server refuses it for a file system root, the server user's home folder or any ancestor of it, and any folder that contains or sits inside another workspace. Rename and delete are refused unless the workspace is ready.

## AI sessions and the live conversation

The AI backend is Live AI (the `Markwardt.LiveAi` library), which drives the `claude`, `codex` or `opencode` command line tool (OpenCode for local models). The server keeps one live session per workspace, opened the first time the workspace is prompted and shared by every client. The tool runs with the workspace folder as its working directory, so the project's own instruction files apply as they do in a terminal (`CLAUDE.md` for Claude Code, `AGENTS.md` for Codex), and its process stays alive between prompts. The tool's own file and shell tools are switched off; the AI works through Live AI's tools instead: file tools over the whole machine, with the workspace folder as the current directory (the folder is not a sandbox, so absolute paths work), and a shell that starts in the workspace folder. A shell command runs to completion, for 120 seconds unless the AI asks for longer (at most an hour), and ends with the prompt. Nothing is ever asked permission for.

That is also what keeps the AI from leaving work behind: without the tool's subagent, background and scheduling tools it does everything itself, and a workspace goes back to Ready when the AI has answered every prompt it was given. The session's instructions say so too: to do all the work in the foreground, reply only when done, and write a short status update as a normal message at least every five minutes (what it has done and what comes next), splitting its work so that no step runs much longer, which keeps the chat from going quiet during a long run since every message of the AI shows in the chat tab.

The session is identified by Live AI's identifier (32 hexadecimal digits), stored as the workspace's `aiSessionId`; Live AI keeps the link from it to the tool's own session in a `liveai` folder in the data folder, and the tool keeps the conversation in its own storage, so it stays usable from the tool itself. A workspace stored by an older server holds the tool's own session identifier (written with hyphens); its first use makes a live session and attaches that conversation to it, so the history and what the AI remembers carry over. When the tool's session has disappeared, or the folder it ran in is gone because the workspace was renamed (a session keeps the path of the folder it started in), a new one starts in its place in the workspace's current folder, with an empty conversation.

A prompt is published as a `MessageAdded` event as soon as the server accepts it, and each message the AI writes as it writes it. A prompt sent while the AI works is steered into the work at once with Live AI's standard send, which is how the user can always add to what the AI is doing. The tools may swallow such a message (Claude Code folds it into a tool result, where the model can dismiss it as noise and the stored conversation does not show it as a message), so the server remembers it and, when the AI's turn ends, checks the stored conversation for it; one the AI did not visibly get is sent again as a turn of its own, with a note that it may have been missed, so it is always worked on. A prompt that arrives as a turn ends (the session is not yet or no longer working) is queued and sent right after, in the order sent. The workspace stays Working across all of these hand-overs and only returns to Ready once nothing is steered or queued any more, so a prompt sent just as the work ends is never lost. Stop forgets what is steered or queued, and so does a failure of the AI. A steered message that the AI did take shows in the live chat but not when the conversation is read back later, since the tool stores it as part of a tool result. If the AI fails (not signed in, out of quota, the tool cannot start) the work ends and the failure is reported as a `Failed` event; the next prompt starts again. Images attached to a prompt are shown to the AI directly; other files it reads by their path.

An idle session is closed after five minutes, and also before a rename, a delete or a service change, so those apply from the next prompt; closing ends the tool's process and loses nothing, since the conversation is stored by the tool. When the server itself stops (SIGTERM or Ctrl+C) it ends the AI's work the same way and waits a few seconds for the commands to end before it exits, so none outlive it.

## Service, model and settings

Each workspace has an AI service, a model of that service and the values of the settings that model offers. The services are Claude Code, OpenAI Codex and OpenCode, which runs the models of servers on the server's machine (Ollama by default, or LM Studio, llama.cpp or vLLM through `localModelUrl`) and those of OpenCode's own configuration; Live AI drives all three the same way, with the same file tools and shell. Models and settings are not a fixed list in the app: the server asks the service for them (`ListModels`) and the clients show what comes back. Claude Code lists its models (and their reasoning effort, which not every model has), Codex what the signed in account offers with its own effort levels, and OpenCode the local models that can call tools, each with a context window setting (the size the local server runs the model with, which OpenCode needs to know to compact in time). A setting is a choice from a list, a switch or a number in a range, each with a default, and the clients draw one control for each: a list, a switch or a number box.

A new workspace uses Claude Code, and its first session starts on the service's default model (Sonnet, or Terra for Codex, otherwise the first model the service lists) with the service's default settings (high effort for Claude Code). The model and the settings do not belong to the workspace but to its AI session: Live AI stores them with the session, writes them when a prompt starts with something other than what is stored, and brings them up to date when the session is loaded (a setting the model no longer has is dropped, a value it no longer takes goes back to the default, and a model that is no longer offered leaves the session without one). The workspace stores only the service. The settings read them from the session (`GetWorkspaceAi`), also when a client opens them again, so a change made from another client shows; a session without a model, whose stored model was retired, shows none selected and refuses prompts with a message to choose one. A choice made before the first prompt is not stored by Live AI yet, so the server keeps it itself and puts it on the session again whenever it closes it, for being idle or for a rename, until the first prompt stores it; a server restart before then loses it, as does the new session a rename starts when the old conversation cannot be continued, which keeps the choice but not the conversation. Choosing a service in the settings lists its models and picks the service's default when it offers it and otherwise the first; the settings refuse to switch to a service that lists no models, for instance because its tool is not installed, and say so. Choosing another model keeps the values of the settings both models have and gives the rest their defaults. The server checks every choice against the service's list before it applies it. The session takes the model and the setting values with its next prompt, so a change applies from then on, including to a conversation that is resumed. Switching the service is refused while the AI works and detaches the AI session, because a session only exists in the service that created it; a new one starts, with an empty conversation. Changing only the model or its settings keeps the session. A workspace stored by an older server also holds a model name and an effort, which are ignored: its session keeps the model it had stored, and a new session starts on the defaults.

## States

A workspace is always in exactly one state: Ready (nothing runs), Working (the AI is running), Running (a script or task is running), Managing (a git action is running), Stopping or Canceling (the work is being ended, below). The server owns the state in one place, a tracker that the prompt service, the script runner and the git workflows each enter when their work starts and leave when it ends, so the check and the change are one step and two requests racing for an idle workspace cannot both win. Work only starts from Ready: a workspace in any other state refuses the others (a prompt while a script runs, a git action while the AI works, a script during a git action, and rename and delete in every state but Ready) with a message naming what is in progress, and the work that holds the workspace has to end first. The one exception is AI input: a prompt or attachment is accepted in Ready and Working, where it joins the work in progress, and refused in Running and Managing.

A git action can use the AI itself to resolve conflicts. That AI work is part of Managing rather than a change of state, so the workspace stays Managing until the action ends, and if the AI is somehow still busy then, the workspace falls to Working instead of Ready. The automatic fetch and pull is not a state: it runs only from Ready, is not reported as busy and does not stop other work from starting. A fetch the user asks for is a git action like any other.

Work in Working, Running or Managing can be ended by hand. Stop ends it at once and keeps what it did: the workspace is Stopping meanwhile and Ready afterwards. Cancel, only for the AI's work (Working), ends it and puts back what it did: Canceling meanwhile, Ready once reverted. Scripts and git actions can only be stopped. Stopping and Canceling are not Ready, so nothing else starts, and they cannot themselves be stopped or cancelled; every other state refuses a second stop or cancel. Stopping the AI interrupts it (the work it did stays in the conversation, which the AI is told, and the next prompt carries on from there); a shell command the AI was running does not end by itself, since it runs in the server, so when one is still running the session is closed as well, which ends the command and the tool's process, and the next prompt opens the session again and resumes the conversation, stopping a script kills the script or the whole task, and a git action cannot be left half done, so stopping it undoes it (the AI that was resolving its conflicts is interrupted too).

Reverting the work of the AI needs a git repository: when the work starts from Ready, the server records a snapshot, the head, the branch, the index and a tree object holding every file git does not ignore, untracked ones included, built in a temporary copy of the index so the real index and files are untouched. Reverting compares that tree with the files as they are, deletes the files and the emptied folders that were added, restores the ones that changed or went missing, then moves the head and branch back (when the work committed or switched branches) and puts the index back. Ignored files, branches the work created and anything it pushed are not reverted. The snapshot is dropped when the work ends normally, and a workspace that is not a repository has none, so Cancel is refused there (Stop is not).

Clients show the state: the header is blue in every state but Ready, the message box is locked in every state but Ready and Working (and says why), buttons that start work are disabled or refuse with a message, and the Managing state offers Cancel and undo for the git action. They work it out from the events and statuses they already receive (the AI working, a script running, a git action busy) and take Stopping and Canceling from the `StateChanged` event, which wins, while the server remains the authority. While the workspace is Working, Running, Managing or Canceling the message box's send button is replaced by the work buttons: Stop in every one of those states (disabled while Canceling, which cannot be stopped) and Cancel only for the AI's work (disabled when the work cannot be reverted). Stop and Cancel are each confirmed with an "are you sure" question that closes by itself if the work ends meanwhile. In Working the send button returns as soon as something is typed, since more AI input is still accepted then.

## Loops

A loop sends one prompt to the AI over and over, for as long as its condition allows. It is set up with a prompt (the review prompt or the user's own), the minutes from the start of one run to the start of the next (zero runs again as soon as a run is done) and a condition that ends it by itself: never, at a time of day (the next time it is), after a length of time (up to 24 days), after a number of runs, or when a usage window of the service reaches a share of its limit (offered only for services that report windows, and read from the service's usage before each run and once a minute while one runs; reaching it also stops the run in progress). The server runs loops itself rather than through Live AI's loop: a run is an ordinary prompt, sent once the workspace is Ready and the AI idle, so a run never overlaps a script, a git action or a prompt of the user, enters Working and captures the snapshot like any other work, and is shown to clients as the user's message with the AI's replies after it. A run is only given when the AI is idle, never steered into or queued behind work it did not start, and not again before the interval since the start of the last run has passed and its work is done, whichever is later (so a prompt of the user, a script or a git action in between delays the next run rather than sharing it). A prompt the user sends while a run works is steered into it and followed up like any prompt, before the next run starts. A workspace has at most one loop, which lives in the server's memory, so it ends when the server stops, and while it runs the server keeps the AI session open (the idle close and the service switch wait for it).

A loop ends when its condition is met, when a run fails (the failure is reported and the loop stops), or when it is cancelled. Cancelling it ends the loop at once but lets the run in progress finish and starts no other. Stop and Cancel end the loop in addition to the run, whatever work they end; renaming or deleting the workspace cancels it first. Clients learn of every start, run and end as a `LoopChanged` event, with the reason when the loop ended by itself, and read the loop with `GetLoop` when they open and reconnect.

## Groups

Workspaces can be filed into groups, which can contain other groups to any depth; the client shows the result as a tree. A group exists only in the server's workspaces file: it is organization for Auto Remote and has nothing to do with the folder hierarchy on disk, so filing a workspace never moves anything and the workspace folders keep their real parents. A workspace is in at most one group and a group has at most one parent. Names are unique ignoring case among the groups with the same parent. A group cannot be moved into itself or into anything inside it. Deleting a group keeps what is in it and moves its workspaces and groups up into its parent (to the top level if it had none). The server keeps workspaces and groups in a custom order that every client shows: new ones go to the end, renaming keeps the place, moving into another group puts the item at the end of it, and the order is changed one place at a time with the shift commands, which only swap among siblings (the workspaces of one group, or the groups of one parent) and stop at the ends. Groups are managed from the workspace listing, not from a workspace's settings, and live server side so every client sees the same organization: the server announces each change with a `WorkspacesChanged` event and clients list the workspaces again, so a workspace created, moved or deleted from one client shows up in the others at once.

## Attachments

Files attached to a prompt are kept in an `attachments` folder in the data folder, one subfolder per workspace, under a name prefixed with a random id, and are deleted with the workspace. The AI reads them by path, as it reads any file.

## History

The server keeps no transcript of its own: the conversation is the tool's stored session, read back through Live AI, so it also shows what was said in the tool outside Auto Remote. The user's prompts and the AI's messages are shown; tool calls, their results and the tool's note that a request was interrupted are left out. The client reads the history in chunks, newest first. A chunk comes with an opaque cursor for the messages before it, which the client sends when the user scrolls to the top, until a chunk has none. Events carry no position, since the stored conversation has none the server could name when a message happens: a client that opens a workspace subscribes first, holds the events that arrive while it reads the newest chunk, and drops from them the leading messages the chunk already ends with. Older servers kept a transcript of their own in a `history` folder of the data folder, which is no longer read and can be deleted.

## Files

Browsing a workspace's files is read only and confined to the workspace folder: paths are resolved and rejected if they leave it. Text files are returned up to 256 KiB, and files that look binary are refused.

The view is live: a connection can watch one folder of one workspace (the one its client is showing), and the server reports changes to that folder, collapsed over a quarter second, so the client refreshes the listing and any open preview. Only the folder itself is watched, not its sub-folders, which keeps watching cheap on large trees; watching another folder replaces the watch, and it ends with the connection.

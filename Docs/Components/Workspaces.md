# Workspaces

A workspace is a folder on the server's machine that the user works in. An AI session is a conversation with the workspace's AI service (Claude Code, OpenAI Codex or local models through OpenCode) that the server creates and attaches to a workspace the first time it is prompted. The two are separate: the workspace is the durable thing the user sees and manages, the AI session is replaceable.

## A workspace is its folder

The server stores three things per workspace: its identifier, the AI session attached to it and the group it is filed in (if any). The folder, the provider and all AI settings are the session's: the workspace's folder is the path the session works in, read from the session when the server starts, and its display name is always the folder's name. Renaming a workspace therefore renames the folder on disk, and the server refuses when another workspace lives inside that folder or the target name exists. Creating a workspace requires an existing folder (the client can create one while browsing, starting from the config's `defaultFolder`), and one folder hosts at most one workspace; the session is made together with the workspace, so a workspace whose session cannot be made (an API key for the local provider, or local models without a model for every capability) is not created at all. Renaming a workspace renames its folder and then tells the AI session; when that fails the folder is renamed back. Moving a workspace to another folder (`MoveWorkspaceToFolder`) is only telling the session: Live AI tracks where a workspace is, and moves the tool's conversation along where the tool keeps it by folder, without loading the session, so it works even when the old folder is gone (the project was moved on disk). The server never moves files for it. A workspace can also be cloned: the server runs `git clone` into a new folder inside an existing one and creates the workspace there.

## Deleting

Deleting removes the workspace and its attachments and ends its live AI session; when the folder is deleted too, the AI service's stored conversation goes with it, otherwise it stays in the service's own storage. Deleting the folder as well is the default and recursive, so the server refuses it for a file system root, the server user's home folder or any ancestor of it, and any folder that contains or sits inside another workspace. Rename and delete are refused unless the workspace is ready.

## AI sessions and the live conversation

The AI backend is Live AI (the `Markwardt.LiveAi` library), which drives the `claude`, `codex` or `opencode` command line tool (OpenCode for local models). The server keeps one live session per workspace, opened the first time the workspace is prompted and shared by every client. The tool runs with the workspace folder as its working directory, so the project's own instruction files apply as they do in a terminal (`CLAUDE.md` for Claude Code, `AGENTS.md` for Codex), and its process stays alive between prompts. The tool's own file and shell tools are switched off; the AI works through Live AI's tools instead: file tools over the whole machine, with the workspace folder as the current directory (files outside the workspace are allowed by default, so absolute paths work), and a shell that starts in the workspace folder. A shell command runs to completion, for 120 seconds unless the AI asks for longer (at most an hour), and ends with the prompt. Nothing is ever asked permission for.

That is also what keeps the AI from leaving work behind: without the tool's subagent, background and scheduling tools it does everything itself, and a workspace goes back to Ready when the AI has answered every prompt it was given. The server builds instructions into every session that say so too: to do all the work in the foreground, reply only when all of it is finished, report its status with the status tool (what it has done and what comes next) at least once every configured interval, give status updates only through that tool and never as normal messages, and make its only normal reply the final summary of what it completed. The interval is a global setting (default 5 minutes) that a workspace can override, and it is part of the instructions, so a change of either rewrites them: in the open sessions at once, in the others when they are opened. The status tool is a tool of the server's own that Live AI serves to the AI of every open session; each call shows the text in the status bar of the chat panel on every client that has the workspace open, and the bar goes away when the work ends. The instructions are stored in the session's instructions in front of the user's own, wrapped in a marker the server recognizes so that an older wording or another interval is replaced, not doubled, and which the server puts there whenever it creates, opens or changes a session (so older workspaces get them too), and takes off again when it reads the settings, so the user never sees them and cannot remove them.

The session is identified by Live AI's identifier (32 hexadecimal digits), stored as the workspace's `sessionId`; Live AI keeps the link from it to the tool's own session in a `liveai` folder in the data folder, and the tool keeps the conversation in its own storage, so it stays usable from the tool itself. Sessions an older server stored with Live AI 1.x are upgraded when the server starts and continue with their history: the link that names the tool's session is rewritten for Live AI 2.0 and the tool's conversation is untouched. A workspace that holds the tool's own session identifier written with hyphens, from before Live AI was used, cannot be continued: it is given a new session with an empty conversation when the server starts, and the old conversation stays in the tool's own storage. When a session can no longer be loaded, a new one replaces it, keeping the workspace and its folder and provider, with an empty conversation. A workspace whose session link is gone altogether stays in the workspaces file but is not listed, since its folder is unknown; it comes back if the link does. When the loaded session's folder is not the workspace's, the session is moved to it.

A prompt is published as a `MessageAdded` event as soon as the server accepts it, and each message the AI writes as it writes it. A prompt sent while the AI works is steered into the work at once with Live AI's standard send, which is how the user can always add to what the AI is doing. The tools may swallow such a message (Claude Code folds it into a tool result, where the model can dismiss it as noise and the stored conversation does not show it as a message), so the server remembers it and, when the AI's turn ends, checks the stored conversation for it; one the AI did not visibly get is sent again as a turn of its own, with a note that it may have been missed, so it is always worked on. A prompt that arrives as a turn ends (the session is not yet or no longer working) is queued and sent right after, in the order sent. The workspace stays Working across all of these hand-overs and only returns to Ready once nothing is steered or queued any more, so a prompt sent just as the work ends is never lost. Stop forgets what is steered or queued, and so does a failure of the AI. A steered message that the AI did take shows in the live chat but not when the conversation is read back later, since the tool stores it as part of a tool result. If the AI fails (not signed in, out of quota, the tool cannot start) the work ends and the failure is reported as a `Failed` event; the next prompt starts again. Images attached to a prompt are shown to the AI directly; other files it reads by their path.

An idle session is closed after five minutes, and also before a rename or a delete, so those apply from the next prompt; closing ends the tool's process and loses nothing, since the conversation is stored by the tool. When the server itself stops (SIGTERM or Ctrl+C) it ends the AI's work the same way and waits a few seconds for the commands to end before it exits, so none outlive it.

## Provider and settings

Each workspace has a provider, chosen when the workspace is created and never changed afterwards, because a session only exists in the provider that created it. The providers are Claude Code, OpenAI Codex and local models (OpenCode, which runs the models of a server on the server's machine such as Ollama, LM Studio, llama.cpp or vLLM); Live AI drives all three the same way, with the same file tools and shell. A new workspace takes the default provider of the AI environment unless the user picks another, and can be given an API key for just its session (Claude Code and Codex), which Live AI stores with the session and the server never keeps.

There is no list of models in the app: a session is configured with a capability (Fast, Balanced, Strong or Max) and an effort (Low, Medium, High or Max), and Live AI picks the model of the provider for them. Besides those the settings hold whether the AI may run shell commands, use files outside the workspace, use the web and generate images, and standing instructions; a new session starts balanced and high, with the web on and the shell, files outside the workspace and image generation off (image generation only works while the environment has an image service), and no instructions of the user's own. Those are the defaults of the AI environment (the `New workspaces` part of it, which is edited with the rest of the environment and applies to every workspace created afterwards, not to existing ones), which the server gives the prompter's environment and Live AI applies to every session it creates, so the server needs no more than the workspace and the provider to make one; a workspace stored by an older release is not given them but what it ran with before (the shell, the web and files outside the workspace on, image generation when there is an image service, and the built-in instructions), once, so that it keeps working as it did. Edits in the settings panel are pending and go to the session together when the panel is closed. Live AI stores all of it with the session, so the settings are read from the session (`GetWorkspaceSettings`), also when a client opens them again, so a change made from another client shows, and written to it (`SetWorkspaceSettings`), applying from the session's next prompt, including to a conversation that is resumed. The server keeps nothing of its own, except that an idle session it closes after a change is simply loaded again. The session also describes how it runs (the model it chose and the settings it runs it with), which the settings show as read only lines.

The AI environment is the one place for what is the same for every workspace: it is applied to the single prompter that all sessions are made on, and the server keeps it in its data folder. The local provider needs a model for every capability there, and a session that cannot be made for lack of it fails with that message.

## States

A workspace is always in exactly one state: Ready (nothing runs), Working (the AI is running), Running (a script or task is running), Managing (a git action is running), Stopping or Canceling (the work is being ended, below). The server owns the state in one place, a tracker that the prompt service, the script runner and the git workflows each enter when their work starts and leave when it ends, so the check and the change are one step and two requests racing for an idle workspace cannot both win. Work only starts from Ready: a workspace in any other state refuses the others (a prompt while a script runs, a git action while the AI works, a script during a git action, and rename and delete in every state but Ready) with a message naming what is in progress, and the work that holds the workspace has to end first. The one exception is AI input: a prompt or attachment is accepted in Ready and Working, where it joins the work in progress, and refused in Running and Managing.

A git action can use the AI itself to resolve conflicts. That AI work is part of Managing rather than a change of state, so the workspace stays Managing until the action ends, and if the AI is somehow still busy then, the workspace falls to Working instead of Ready. The automatic fetch and pull is not a state: it runs only from Ready, is not reported as busy and does not stop other work from starting. A fetch the user asks for is a git action like any other.

Work in Working, Running or Managing can be ended by hand. Stop ends it at once and keeps what it did: the workspace is Stopping meanwhile and Ready afterwards. Cancel, only for the AI's work (Working), ends it and puts back what it did: Canceling meanwhile, Ready once reverted. Scripts and git actions can only be stopped. Stopping and Canceling are not Ready, so nothing else starts, and they cannot themselves be stopped or cancelled; every other state refuses a second stop or cancel. Stopping the AI interrupts it (the work it did stays in the conversation, which the AI is told, and the next prompt carries on from there); a shell command the AI was running does not end by itself, since it runs in the server, so when one is still running the session is closed as well, which ends the command and the tool's process, and the next prompt opens the session again and resumes the conversation, stopping a script kills the script or the whole task, and a git action cannot be left half done, so stopping it undoes it (the AI that was resolving its conflicts is interrupted too).

Reverting the work of the AI needs a git repository: when the work starts from Ready, the server records a snapshot, the head, the branch, the index and a tree object holding every file git does not ignore, untracked ones included, built in a temporary copy of the index so the real index and files are untouched. Reverting compares that tree with the files as they are, deletes the files and the emptied folders that were added, restores the ones that changed or went missing, then moves the head and branch back (when the work committed or switched branches) and puts the index back. Ignored files, branches the work created and anything it pushed are not reverted. The snapshot is dropped when the work ends normally, and a workspace that is not a repository has none, so reverting is refused there (Stop is not). No client offers it: the clients only stop work, and cancel only a loop.

Clients show the state: the header is blue in every state but Ready, the message box is locked in every state but Ready and Working (and says why), buttons that start work are disabled or refuse with a message, and the Managing state offers Cancel and undo for the git action. They work it out from the events and statuses they already receive (the AI working, a script running, a git action busy) and take Stopping and Canceling from the `StateChanged` event, which wins, while the server remains the authority. While the workspace is Working, Running, Managing or Canceling the message box's send button is replaced by the work buttons: Stop in every one of those states (disabled while Canceling, which cannot be stopped). Stop is confirmed with an "are you sure" question that closes by itself if the work ends meanwhile. In Working the send button returns as soon as something is typed, since more AI input is still accepted then.

## Loops

A loop sends one prompt to the AI over and over, for as long as its condition allows. It is set up with a prompt (the review prompt or the expand prompt in use for the workspace, or the user's own), the minutes from the start of one run to the start of the next (zero runs again as soon as a run is done) and a condition that ends it by itself: never, at a time of day (the next time it is), after a length of time (up to 24 days), after a number of runs, or when a usage window of the service reaches a share of its limit (offered only for services that report windows, and read from the service's usage before each run and once a minute while one runs). The server runs loops itself rather than through Live AI's loop: a run is an ordinary prompt, sent once the workspace is Ready and the AI idle, so a run never overlaps a script, a git action or a prompt of the user, enters Working and captures the snapshot like any other work, and is shown to clients as the user's message with the AI's replies after it. A run is only given when the AI is idle, never steered into or queued behind work it did not start, and not again before the interval since the start of the last run has passed and its work is done, whichever is later (so a prompt of the user, a script or a git action in between delays the next run rather than sharing it). A prompt the user sends while a run works is steered into it and followed up like any prompt, before the next run starts. A loop can be started while the AI is working, and its first run then waits until that work is done. A workspace has at most one loop, which lives in the server's memory, so it ends when the server stops, and while it runs the server keeps the AI session open (the idle close and the service switch wait for it).

A loop ends when its condition is met, when a run fails (the failure is reported and the loop stops), or when it is cancelled. Ending a loop never cuts off work: whether its condition is met or it is cancelled, the run in progress finishes and the loop only stops sending prompts. Stop and Cancel end the loop in addition to the run, whatever work they end; renaming or deleting the workspace cancels it first. Clients learn of every start, run and end as a `LoopChanged` event, with the reason when the loop ended by itself, and read the loop with `GetLoop` when they open and reconnect.

## Groups

Workspaces can be filed into groups, which can contain other groups to any depth; the client shows the result as a tree. A group exists only in the server's workspaces file: it is organization for Auto Remote and has nothing to do with the folder hierarchy on disk, so filing a workspace never moves anything and the workspace folders keep their real parents. A workspace is in at most one group and a group has at most one parent. Names are unique ignoring case among the groups with the same parent. A group cannot be moved into itself or into anything inside it. Deleting a group keeps what is in it and moves its workspaces and groups up into its parent (to the top level if it had none). Groups have a custom order that every client shows: new ones go to the end, renaming keeps the place, moving into another group puts the group at the end of it, and the order is changed one place at a time with the shift command, which only swaps among sibling groups (those of one parent) and stops at the ends. Workspaces have no manual order: within a group (or at the top level) clients list them by when their AI session was last loaded, the latest first, and the server reads that timestamp from Live AI whenever the workspaces are listed and announces a change when a prompt is sent so the order follows the work. Sub-groups are listed before the workspaces, and groups start collapsed, except that focusing a workspace opens the groups around it. A new workspace can be filed into a group when it is created or cloned. Groups are managed from the workspace listing, not from a workspace's settings, and live server side so every client sees the same organization: the server announces each change with a `WorkspacesChanged` event and clients list the workspaces again, so a workspace created, moved or deleted from one client shows up in the others at once.

## Attachments

Files attached to a prompt are kept in an `attachments` folder in the data folder, one subfolder per workspace, under a name prefixed with a random id, and are deleted with the workspace. The AI reads them by path, as it reads any file.

## History

The server keeps no transcript of its own: the conversation is the tool's stored session, read back through Live AI, so it also shows what was said in the tool outside Auto Remote. The user's prompts and the AI's messages are shown; tool calls, their results and the tool's note that a request was interrupted are left out. The client reads the history in chunks, newest first. A chunk comes with an opaque cursor for the messages before it, which the client sends when the user scrolls to the top, until a chunk has none. Events carry no position, since the stored conversation has none the server could name when a message happens: a client that opens a workspace subscribes first, holds the events that arrive while it reads the newest chunk, and drops from them the leading messages the chunk already ends with. Older servers kept a transcript of their own in a `history` folder of the data folder, which is no longer read and can be deleted.

## Files

Browsing a workspace's files is read only and confined to the workspace folder: paths are resolved and rejected if they leave it. Text files are returned up to 256 KiB, and files that look binary are refused.

The view is live, also for changes made outside Auto Remote: a connection says which workspace its client is showing, and the server watches that workspace's whole folder, sub-folders included, for as long as some connection has it open (and gives up the watch when the last one leaves, or the workspace is renamed or deleted). Changes are collected until the folder has been quiet for 0.4 seconds, or for two seconds at most while it keeps changing, and then reported to every connection as one `FilesChanged` event per folder whose entries changed (more than 200 folders collapse into one event for the workspace folder marked `all`, meaning anything may have changed). Everything inside `.git` is ignored except the head, the index, the packed refs and the refs, which are reported as `GitChanged`, since a commit or checkout from a terminal moves them. A client refreshes the folders it shows and reads the git status again, and re-reads the open file when its folder changed, at most once every three seconds however often it changes, and only replaces what is shown when the content differs. If the operating system cannot watch the folder (the limit of watches is reached, for example), the server logs it and carries on without live updates for that workspace.

# Swarm

Several Auto Remote servers on different machines can share work, mainly to spread it across local AI. A server that delegates (the coordinator, for that task) hands another one (the worker) a self-contained task: instructions plus the code. The worker runs it on its own local models and sends back a commit that the coordinator turns into a branch, whose changes the coordinator's AI brings into the workspace. Every server can be both at once, and every server stays usable directly. Delegated work runs through the local AI work queue like any other work, after direct work.

The unit is always the same sealed task package and result package; the delivery modes differ only in how the packages and the code travel, which keeps one code path for networked and air gapped use.

## Delivery modes

Each side sets the mode for each paired server, so one swarm can mix them. The coordinator's mode decides how the code travels.

| Mode | Code | Packages |
| --- | --- | --- |
| `GitRemote` | Branches under `swarm/` on the project's `origin`, which both reach with their own credentials | Over a connection between the two |
| `Direct` | Git bundles inside the packages | Over a connection between the two |
| `AirGapped` | Git bundles inside the packages | A drive, synced by hand on each machine |

A server set to `AirGapped` for a peer neither connects to it nor takes its connections. A project without an `origin` remote, or a worker that cannot fetch it, fails the task with that reason rather than falling back to bundles.

## Trust

Each server has an identity, an ECDSA signing key and an ECDH key (P-256), made when the server first starts and, except on Windows (where the data folder's own permissions apply), readable only by the server's account. Its identifier and the fingerprint people compare are a hash of both public keys. Every package is encrypted to its receiver (AES-256-GCM with a key derived from the two ECDH keys and a random salt) and signed by its sender, over network and drive alike; a package that is unsigned, changed, from a server that is not paired or addressed to someone else is refused. Trust therefore never rests on TLS certificates, which are self-signed and not checked between servers.

Pairing is mutual and leaves everything off. Over a network, one server makes a code (random, shown once, valid 15 minutes, spent by its first use and withdrawn after five wrong attempts) and the other sends its public keys with an HMAC over them keyed by the code; the reply proves the code back over both sets of keys, so a machine in the middle cannot swap either. By drive, one writes a signed invitation, the other confirms it and writes a signed acceptance that the first confirms. A signature only shows the writer holds the keys, so both confirmations ask the person to compare the fingerprint.

Work flows only when the coordinator sends work to that peer, and the worker both accepts delegated work at all and accepts that peer's. For its AI delegating (not the user by hand), the workspace must also allow it. A delegated workspace never delegates further.

A network connection from a peer uses the server's normal port with a handshake that carries no access key. Such a connection gets no events and no commands: it can only pair with a code or, after a signed hello (fresh within 15 minutes and never accepted twice while the server keeps running), exchange sealed packages. Until it has done one of those it may send only small messages, and only a few such connections (three per address) are held at once, apart from the connections of paired servers.

## What a delegated task may do

A worker runs a task with the permissions its owner set for that sender: sandbox, web and image generation (images only with a local image server, so no cloud key is spent), all off by default. It runs only on the worker's local models, never with its Claude or OpenAI keys. Without the sandbox the AI has a shell and its file tools reach outside the workspace, so a task can reach everything the server's account can: a worker that does not fully trust a sender turns the sandbox on for it (no shell, and no files outside the workspace except what the server shares), or runs under an account of its own. While a workspace runs a delegated task the server refuses further prompts, settings changes, loops, renames, moves, scripts, side sessions and git commands for it; its owner can still watch it and stop, cancel or delete it (which the coordinator is told).

Two things in a sender's files could run commands on a worker even for a sandboxed task, and both are closed:

- OpenCode loads the plugins and MCP servers a project configures as soon as a session starts in it. Before a worker makes a delegated session it sets `OPENCODE_DISABLE_PROJECT_CONFIG` in its own environment, which Live AI passes on to OpenCode; it stays set as long as the server runs (a server that restarts itself without a service manager hands it on), so from then on no local workspace of that server loads project level OpenCode configuration. As a second line of defense, the configuration of AI tools (`.opencode`, `.claude`, `.codex`, `opencode.json`, `opencode.jsonc`, `.mcp.json`, at any depth) is never written into a task's folder, the worker never takes changes to it, and the coordinator refuses a result that changes any of it, since bringing it in would configure the coordinator's own tools. The read only copies of results never hold it either.
- git looks inside nested repositories while adding files and runs whatever their configuration says. Before collecting a result the worker deletes every nested `.git`, keeps git out of submodules (their entries stay as the base has them) and reads no git configuration but the cache's.

A delegated workspace also keeps the AI session its restrictions were set on: if that session cannot be loaded the task fails, where any other workspace would get a new session with the owner's defaults. A server that restarts while it is setting a task up first removes what it had made (the folder, and a workspace that may not have been restricted yet) and starts over.

The folder of a task is deliberately not a git repository. The worker keeps a bare cache repository per sender and project, which only the server writes, and exports the task's files with `GIT_DIR` pointing at that cache. Collecting the result runs git the same way, so nothing the AI writes into the folder (such as a `.git` with a `core.fsmonitor` command or a hook) can run with the server's rights. The cache sets `core.symlinks` to false, so symbolic links in the code arrive as plain files and cannot lead the file tools outside the workspace. In `GitRemote` mode the worker uses its own git credentials on an address the sender names, so it only does so for a sender whose delivery mode its owner also set to `GitRemote`, and only for network addresses (HTTP, SSH, git), never a local path or a remote helper such as `ext::`, which would let a sender read the worker's own repositories or run commands.

## Code and results

Delegating needs the workspace to be the root of a git repository with a commit. The snapshot is the current commit, or, when anything is uncommitted or untracked, a temporary commit on top of it made through a copy of the index, kept under `refs/auto-remote/`: no branch, file or staged change moves. Ignored files are never sent. A bundle leaves out the commits the worker is known to have (the bases of its finished tasks); a worker that lacks one answers that history is missing and the task is sent once more with all of it. Git LFS contents and submodules are not carried.

The worker commits whatever the folder holds, ignored files aside, as one commit on the base, whatever the AI did with git itself. A delegated workspace has `report_unfinished`: a task whose AI calls it ends as failed with that reason, but still sends back what it changed. The coordinator checks that the result's only parent is the task's base and makes a branch `swarm/<id>-<title>` for it; its branch history includes the temporary commit when there were uncommitted changes.

A result also carries the worker's final report (the instructions of a delegated workspace ask for what changed, how it was checked and what is open) and the conversation with its work. The coordinator keeps both. The worker removes the task's workspace and folder once the coordinator has acknowledged the result.

## Bringing results in

The server never merges or applies a result: the base is usually behind the workspace by then, and what to keep is a judgment the AI can make and test. For each result it writes a copy outside the workspace, in the server's data folder: all files as the task left them (no repository and no links, even where the coordinator's repository would make them), the list and diff of its changes against the task's base, and the report. The copy is shared with the workspace's AI read only, and the AI is given a turn of its own to bring it in, with all results that are ready at once so it can combine them, and told which results should already include which. It confirms each with `finish_integration`, the tool that also confirms side sessions, which removes the task with its branch, references, copy and, in `GitRemote` mode, its branches on the remote (deleted afterwards, so a slow remote holds nothing up). The activity of the workspace keeps the report and the changed files.

Whether a result is brought in by itself is the task's `Bring Into Main` setting: on for tasks the AI delegates and by default for those delegated by hand, off for tasks stored by versions that had no such setting, which wait until the user asks. Asking brings a finished result in at once, even while the rest of its job runs. Turning the setting off also takes back a turn that still waits for the local AI; one the AI already has goes on. Whether the changes are committed afterwards is a setting of each waiting result (on by default); a turn commits if any of its results asks for it.

A turn follows the rules of other automated work: it waits until the workspace is free (never joining other work), after a commit that is due and work tried again, and before queued inputs and loop runs; it waits while the chat is stopped, while the side session it goes into is not ready, and at a usage limit. A turn the AI could not have (it could not start or run) or that was stopped counts for nothing and is given again, ever more rarely while the AI cannot run. A result still not confirmed after two turns, or after the AI reported that it cannot finish, stays with its task, which says it needs attention, with `Bring Into Main` off; the next turn of the AI is told, and nothing else is held up. A turn is stored with what it asks: after a restart the scheduler resumes one that told about delegated tasks, with the same copies shared again under the same identifiers, and any other is asked for anew.

`Continue Here` instead turns a finished task into a side session for the user to go on with: its worktree is on the commit that was checked out when the task was delegated, with the files as the task left them, and its changes since the start are measured against the task's base. Its AI is a copy of that of the workspace the task came from, its chat starts with the report, it is kept separate until the user brings it in, and the task is removed. For a task a side session delegated, the new session belongs to the same main workspace.

Discarding a task deletes its branch, references and `swarm/` branches on the remote without bringing anything in.

## Scheduling

A task waits for the tasks it depends on, then for a worker; if one of them does not finish it is cancelled. The server does not merge their results: the dependent task keeps the snapshot as its base, and the results travel beside it (their commits in the bundle, or as `swarm/dependencies/` branches). The worker writes each out as a read only folder (files, changes, diff, report) outside the task's folder, and its AI is told to combine them into its files before doing the task, so a chain needs no review round in between and conflicts are the AI's to decide. The dependent result therefore holds their changes too. A task takes a copy of what it builds on once all of it is done, or when one of those results is brought in while it still waits for others, so bringing one in never breaks the chain.

A worker's profile carries a protocol version, and a task that builds on changes is only given to a worker new enough to combine them (an older one would silently do the task without them). Until such a worker can take it, the task stays pending and says why. A task that names an air gapped worker known to be too old fails with that reason, since nothing more is learned about it until the drive is synced; while its version is not known yet it waits.

A networked worker only gets a task when it was heard from in the last 90 seconds (what a worker said before it was switched off says nothing) and its profile says it accepts the sender's work, offers the capability (`Fast`, `Balanced`, `Strong` or `Max`, each served by the worker's own local model) and has a free slot. Free slots come from its work queue: in `Yield` mode one when nothing runs or waits, otherwise what is left of its delegated limit. Until then the task stays on the coordinator, where another worker can take it. A task for any worker goes to one that has the model of its capability loaded, if there is one (a worker asks its Ollama which are), otherwise to the one with the most free slots. An air gapped worker cannot be asked, so an air gapped task must name it and is sent right away; it then waits in the worker's queue.

States: waiting for other tasks, pending (for a worker), in transit (sent, not acknowledged, as while a drive carries it), queued, running, done, failed, cancelled and lost. A task in transit, queued or running whose networked worker has not been heard from for three minutes becomes lost (each part of a package in transfer counts as hearing from it); time in which the coordinator was not listening, because it was stopped or its machine asleep, does not count. Tasks that depend on a lost one keep waiting, and if the worker comes back the job is reported to the AI again once it ends. A lost task is never resumed elsewhere (AI sessions are stateful and work is not idempotent); retrying it delegates it again from the same instructions and code, and cancels the old one, but a result arriving before that is still taken.

## Delivery

Each server keeps an outbox per peer holding tasks, results and cancellations until the peer acknowledges them; profiles, acknowledgments and progress are made fresh for each delivery. Packages are named so they sort in the order they were posted, so a cancellation never overtakes its task, and every task, result and cancellation is handled once however often it arrives (handled identifiers are kept 90 days, and a task made longer ago than that is answered as failed, never run). A cancellation that arrives before its task is remembered, so the task is not run.

A task counts as handled on the worker only once its code is stored, and a periodic sweep picks up any task left neither running nor ended, and removes what is left of an ended one whose result arrived. A task whose code is still being packed or pushed when it is cancelled, or when its worker stops receiving work, is not given to anyone under the same identifier, since the worker may already have been told to drop it: unless cancelled it fails, and can be retried. A cancellation never waits for a result that is being sent; the result then says it was cancelled. A failure that may pass by itself, such as a git command that cannot reach the remote, takes too long or meets a lock, does not end a task: a worker keeps the task active and tries to send the result again, and a coordinator leaves a result it cannot take unacknowledged so that it arrives again. A package that waits for its acknowledgment is sent again at most once a minute over the same connection, and a drive keeps the file of one that was not taken, with the reason in the sync report. Both sides give up only after at least three attempts spread over 30 minutes or more; a result that is wrong in itself fails at once. After a restart the worker applies the task's permissions again before resuming it, and a task whose AI was still working fails as interrupted; one the AI had finished is only sent back.

Over a network, the side that has an address for the other connects (usually the worker, so only the coordinator has to be reachable; through a VPN over the internet) and the two take turns: it sends its mail and the other takes it in and replies with its own. Rounds are a second apart while tasks are under way, five otherwise. While tasks run, progress carries their state and new messages, which the coordinator keeps and shows live. A failing connection is retried with growing pauses and its reason shows on the peer. A connection is dropped for silence, never for the time a large package takes on a slow link. Sending code, which for a git remote means a push, happens apart from receiving, so a slow push does not hold the connection that brought a result. Revoking a server first stops everything with it and then ends its tasks.

By drive, `Sync Drive` first takes in everything under `auto-remote/mail/<this server>/` from paired servers, then writes each air gapped peer's mail under `auto-remote/mail/<peer>/<this server>/` and removes what is no longer waiting, so one drive can go round several machines. The drive is a folder on the server's machine, not on the client's. Results and cancellations only move with the drive: a cancellation can arrive after the work is done. Workers need their models, tools and package caches installed beforehand, since a task cannot download them.

## AI delegation

A workspace that allows delegation offers its AI the tools `list_workers`, `delegate_tasks`, `task_status`, `cancel_task` and `review_task`, added to its Live AI session's own tools. The last three stay while the AI has delegated tasks it has not dealt with: ones under way, results not brought in, and failed, cancelled or lost tasks until they are discarded. The tools only ever reach the tasks of their own workspace. `review_task` exists because the AI may have no shell to run git with, and only shows. The coordinator's AI can be any provider; the workers always use local models. Side sessions delegate too, and their results come back to them; a side session is not brought into its main workspace while its tasks are under way or their results are not in yet, and one that is being brought in takes nothing.

The AI must end its turn after delegating rather than wait: results can take days by drive, and in `Yield` mode a coordinator waiting inside its turn would hold the only slot a task for its own machine could need. While tasks are under way the workspace's queued inputs and loop wait, though other results can still be brought in. Once every task of a job has ended, the AI gets one turn that lists each outcome, including failed, lost and cancelled tasks for it to deal with, and asks it to bring in the finished results. The job counts as told only once that turn started, so it reaches the AI even after a restart or in a new session. A job has at most the number of tasks set on the coordinator (10 by default). The AI is not told about jobs the user delegated by hand; their results are brought in one by one as they finish.

Deleting a workspace that delegated tasks cancels those under way and forgets the records, conversations and copies of all of them. It removes the references kept for the tasks and, in `GitRemote` mode, the `swarm/` branches on the remote (as far as the remote answers within 20 seconds); the local `swarm/` result branches stay, since they may hold work that was not brought in.

Actions of the user never wait for a send that takes long, such as a push over a slow link: after a moment the send goes on by itself.

A client holds back a ready notification while the workspace has delegated tasks under way or results waiting for their turn, so it arrives when the AI has dealt with them. Tasks that only wait on a lost one do not hold it back, since the AI is told about their job.
